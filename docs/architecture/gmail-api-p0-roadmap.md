# P0 — implementation roadmap and acceptance

Date: 2026-10-09. Status: proposed gates after owner P0 review. [Architecture](gmail-api-p0-fresh-install.md), [database design](gmail-api-p0-database-design.md) and ADRs 0012–0015 are the design inputs. This is a plan for a complete Gmail provider on a fresh installation, not an account-migration program.

P1–P4 are reviewable increments toward one complete provider, not separately deployed partial receiving modes. Future releases must include the `test` hotfix and intervening approved fixes from the implementation baseline. P0 does not authorize merging the PoC or changing production code. Gmail API sending, Pub/Sub wakeups and cloud draft synchronization are outside this roadmap and require a separate request.

## Correctness and regression acceptance

These are scenario/benchmark **criteria**, not new tests. Under the user's repository instructions, do not create or modify unit/automated tests without an explicit later request. Future implementation may run appropriate existing checks and use a separately authorized manual staging protocol; request separate authorization if new automated coverage is desired. No test files or tests are changed/run by P0.

| Area                               | Required observable result                                                                                                                                                                                                                                                                                             |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fresh DB and security              | Empty DB reaches final schema via shipped history plus new DDL; conditional checks/partial unique/composite ownership prevent invalid states; runtime uses ordinary scoped owner; native backup restores only in supported matched release                                                                             |
| Google OAuth/UI setup              | Same Settings Client ID/Secret, tile, start/callback/reconnect and requested scopes; rotated tokens/subject validation preserved; no separate setup or selector; revoked/disabled API/admin policy distinctly actionable                                                                                               |
| Routing/non-Google                 | Every Google discovery/recent/backfill/delta/refresh/content/attachment/command path uses REST; no Google IMAP fallback on errors. Microsoft/password IMAP and SMTP remain unchanged, including UID presence/STATUS/epoch/lifecycle fixes and dependency patches                                                       |
| Identity/labels                    | Same Gmail ID in Inbox/Sent/custom labels is one message and multiple memberships; duplicate ingestion returns same UUID; cross-account IDs remain separate; renamed/deleted label does not rename/delete message identity; no fabricated protocol numbers                                                             |
| Bootstrap                          | Empty account, multipage recent/full inventory, many labels, Spam/Trash, ignored DRAFT IDs and changing mailbox during scan; recent rows before old history, zero body downloads solely for inventory, complete unique ID coverage verified independently                                                              |
| History                            | Repeated events/pages, added then deleted mail, label departures, huge decimal history, truncated JSON and failure at each page/item/commit; durable checkpoint advances only after complete work; no label filters or guessed later profile checkpoint                                                                |
| Crash and locking                  | Interrupt before/after stage commit, projection commit, checkpoint commit and queue ACK; restart/duplicate worker resumes idempotently. Loss of advisory-lock session prevents publication. Pool=1, expired-token refresh, reconnect/disable/delete and concurrent UI command do not deadlock or publish stale results |
| Expiry                             | History 404 starts native complete ID/label repair; interrupted repair never removes data based on incomplete enumeration; cached content/blobs/UUIDs survive; exact message 404 and credential errors are distinguished                                                                                               |
| Actions/counts                     | Read/star updates all labels, archive removes Inbox while retaining user labels, native Trash is never permanent delete. Pending intent survives concurrent history/backfill. Whole-label unseen totals are not replaced with loaded recent counts; no double optimistic correction                                    |
| Reader/security                    | Same sanitized content, isolated rendering/remote-image policy, charset and multipart selection, CID and attachment/encoded/decoded limits, cached policy refresh and request/attempt fencing; malformed/large parts fail safely through current reader feedback                                                       |
| Compose/drafts                     | Reply/forward/header evidence/Bcc envelope and incoming attachment pins preserved; local autosave/revision conflict/browser recovery work in two tabs/restart; remote DRAFT is not adopted as a local draft                                                                                                            |
| SMTP/Sent                          | Accepted/definite failure/uncertain outcomes stay distinct; uncertain send never auto-retries. Native Gmail SMTP produces one received SENT identity; delayed/multiple observation candidates never cause MIME upload, identity merging or duplicate send; custom Sent label policy follows reviewed P0 choice         |
| Search/conversations/notifications | One search hit per logical message with deterministic mailbox; existing RFC header grouping/preference preserved; no claim of body coverage not fetched. Backfill/recovery suppress old arrival flood; live Inbox arrival emits once across labels/replays                                                             |
| Visual parity                      | Compare `test` and native build in light/dark, empty/loading/error, keyboard/list/conversation/reader/composer/settings states. Only labels/folders, Google connection details and Gmail sync diagnostics may differ                                                                                                   |

Every future scenario record should include workload/build/schema version, reproduction, final projected state and checkpoint, not just HTTP call counts. Use dedicated authorized staging mailboxes/grants and synthetic fixtures; never production tokens or mailbox contents in artifacts. Manual protocol changes are performed only in that later stage, not during P0.

## Performance and quota acceptance

Proposed thresholds awaiting workload/hardware review; no observed performance claim. Use approximately 41,000-message and smaller staging accounts with one/many labels, representative MIME and attachments, and 1/4 concurrent accounts. Record VPS/DB/pool/network, effective Cloud quota, fetch field masks, cold/warm status and contention. At least 100 warm samples for percentile claims, three cold runs and rotated concurrency order. Include OAuth refresh, queue, HTTP/body parsing, DB/conversation/search, sanitizer and blobs in end-to-end timings.

| Measure                      | Proposed acceptance                                                                                                                                                                                                                                   |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Empty delta                  | Worker-start-to-commit warm p95 ≤2 s under quota headroom; single history page and no message GET or full inventory absent catalog cadence; report OAuth/queue separately                                                                             |
| Four changed messages        | Warm p95 ≤3 s from worker start to durable projection/checkpoint; work scales with changed IDs/pages, exact final state                                                                                                                               |
| Recent-first availability    | Publish recent-window completion time separately from full inventory; recent rows usable while backfill continues. Set a concrete latency budget after measured recent workload and effective quota, not an invented universal ETA                    |
| 41k complete inventory       | 100% unique remote non-deleted IDs accounted for and correct eligible memberships; no automatic body/attachment downloads; publish elapsed time, request/unit totals, retries and coverage; no full-import time promise from PoC sample               |
| Reader/commands under import | p95 at most 20% worse than measured no-import Gmail baseline; no starvation and bounded account slices; report absolute latency as well as ratio                                                                                                      |
| Resource use                 | Initial proposed worker RSS ≤512 MiB for the measured workload; no RAM growth proportional to entire mailbox/history; data transaction p95 ≤500 ms at selected batch size; representative largest supported attachment stays within configured limits |
| Quota/fairness               | Shared account/project budget and interactive reserve respected across workers; honor Retry-After without retaining DB locks; bounded in-flight pool; one blocked account does not starve another                                                     |
| Native recovery/restore      | Stable local UUID/cache/blob hashes across a native backup/restore and expired-history repair; recovery completeness/time measured on 41k account, no full body redownload                                                                            |

Use current published cost 20 units per metadata GET when planning; effective old-project quotas may differ. Reserve and retry overhead make import time higher than the quota-only minimum. No migration/alias/rollback/cache-conversion benchmark is required. Correctness gates cannot be relaxed to meet a latency target. If a proposed latency/resource threshold needs revision, review the measurement and budget before release.

## Future fresh-install procedure gate

Before any later operator reset, approve the release and date, review pending/uncertain SMTP work, stop all old writers/ingress, preserve a matched old backup if desired, and provision a separate empty database/blob namespace with scoped ownership. Use standard owner/MFA setup and the existing Settings/OAuth flow to configure/reconnect accounts. Inform the owner about local draft/preference/signature/cache/outgoing-history loss and new UUIDs. Verify remote mail remains intact and the new receiver performs native import. Reset/delete commands are not included or executed by P0.

Post-release failures are handled by pausing native account work, fixing/retrying it, restoring a matched native installation or re-enumerating native Gmail state. Whole-release recovery of a separately retained old installation is an operator choice with send-uncertainty review; it is not an automatic Gmail transport fallback.
