# External Gmail read-status latency diagnosis

Scope: commit `5efc23c9`, checked against the currently running container's compiled worker. Diagnosis only. All diagnostic Gmail traffic used `SyntheticGmail` and disposable PostgreSQL; the running database was inspected with SELECT queries only. No real messages, sync state, import state or production behavior were changed.

1. **Confirmed cause and limits of the conclusion**

The application couples authoritative unread-counter sampling to history-sweep boundaries. After import finishes, it also sleeps for 60 seconds **after checkpoint completion**, rather than polling history every 60 seconds independently of processing. These are verified latency bottlenecks. There is no separate receive path that polls external read changes less frequently than new messages: both use account-wide `history.list`.

For a quiet, fully imported account with fresh Gmail responses, a single external read requires **two productive worker passes to publish the counter**, not two minute-long waits. Approximately 120 seconds is reproducible when the change happens during a sufficiently long history sweep. It is also reproducible with stale label responses or a 60-second API backoff. Which condition caused the reported real test is **not confirmed** by the available logs.

Relevant functions: [GmailSyncService.run/history/labels/counter/drain/inventory](D:/Projects/JS/Maildock/src/modules/mail/application/gmail-sync-service.ts:77), [GmailPoller/enqueueGmail/registerGmailWorker](D:/Projects/JS/Maildock/src/modules/mail/infrastructure/gmail-sync-jobs.ts:26).

`5efc23c9` correctly puts INBOX first among four label-counter requests, fetches history before refreshing labels, and adds another INBOX refresh before committing changed history. It did **not** change the 60-second deadline, the control-only startup pass, or the lack of counter refresh during history-page draining and subsequent pages. The final refresh occurs only when `historyCandidateId !== historyStartId`. The patch therefore reduces label-rotation starvation without providing a freshness bound.

2. **Complete pipeline and timers**

| Eligibility          | `GmailPoller.start()` polls immediately, then every **1 second**; overlapping polls are suppressed. Selects up to **20** enabled, connected Gmail accounts, ordered by sync-state update time. `next_attempt_at`, not `needs_work`, controls eligibility.                                                                                                                                                                                                                                                                                                              |
| Enqueue              | `enqueueGmail()` marks work needed, writes `next_attempt_at=now()` when there is no error, and sends a singleton-key job at priority **5**. This can leave a redundant queued delivery when a preceding job publishes a future deadline. Explicit wake/manual refresh also clears a normal idle deadline; external Gmail actions do not invoke this.                                                                                                                                                                                                                   |
| Consumer             | pg-boss default polling is **2 seconds**, with **2** local consumers, batch size **1**. Queue policy is `stately`: one queued and one active job per account/state, not a 60-second throttle. No NOTIFY is enabled on the live Gmail queue. Continuations become eligible immediately and are recovered by the 1-second poller; they are not explicitly dispatched immediately by the service.                                                                                                                                                                         |
| Account authority    | Each delivery first acquires fresh OAuth credentials, then a session advisory account lock. OAuth refresh uses a row lock and **15-second** HTTP timeout on every acquisition, including no-op deliveries. Gmail authority uses `pg_try_advisory_lock`: contention throws rather than waiting indefinitely. A pending Maildock command defers background work **1 second**; this is unrelated to the external read itself.                                                                                                                                             |
| Idle history startup | First productive pass creates `historyRunId` and fixes `historyStartId`, then returns without Gmail history or label HTTP calls. | Durable work         | History requests use `maxResults=100`. All message references, additions, deletions and label changes feed a deduplicated queue, fragmented at **500** identities. `stagePage()` commits work and pagination state together. | Checkpoint           | A draining pass returns even when it completed the last item; a later pass finalizes. Cursor advances only after pages and work finish. It neither calls Gmail nor wakes sync. `synchronizedMessageCount` is a separate local count, not unread authority.                                                                                                                                                                                                                                           |
| UI                   | [MailClient](D:/Projects/JS/Maildock/src/components/mail-client.tsx:1005) polls Gmail mailbox counters every **10 seconds**, messages every **20 seconds**, with `cache: no-store`. Zero removes the badge. |

Other relevant delays: worker Gmail clients explicitly use **zero HTTP retries**, despite the generic client's default of two retries with approximately 1–2/2–3 second jitter. Gmail REST timeout is **15 seconds**. Caught Gmail failures persist `nextAttemptAt = now + max(retryAfter, 30 seconds)`; authentication/access/API-disabled failures use **300 seconds** and authentication is refreshed once immediately outside authority. Quota reservations preserve the background **70%** ceiling: rolling minute buckets can defer approximately **61 seconds**; daily exhaustion waits until UTC midnight. These failures are handled as successful queue deliveries, so queue retry count zero does **not** rule out API backoff.

Unhandled failures, including account-lock collisions, use pg-boss **4 retries**, exponential jitter initially **30–60 seconds**, capped at **900 seconds**; job expiry is **180 seconds**. pg-boss supervision/monitoring default to **60 seconds**, relevant to recovery/expiry, not ordinary dispatch. Worker readiness is checked every **1 second**; failed readiness pauses all business work. Hourly event retention and the 60-second content-recovery timer do not schedule Gmail history. IMAP delta/backfill/IDLE timers exclude native Gmail accounts, so they do not accelerate this pipeline. There is no Gmail push/watch receiving implementation here.

Inventory interaction: initial recent inventory completes before the first catch-up. During historical import, staging each new inventory page creates a history run, which takes precedence on subsequent deliveries. After that catch-up, inventory's current page drains in up to nine passes for 100 identities before the next page/catch-up. Inventory refreshes counters when some are unknown, but does not periodically refresh already-known counters. Final unseen-identity reconciliation can also run many slices before another catch-up. Once historical import is complete, this inventory path disappears; the 60-second post-checkpoint idle path remains.

3. **Timelines and expected latency**

Quiet account, one known message, immediate consistent Gmail responses:

- External read occurs during the normal idle deadline.
- Remaining idle wait: 0–60 seconds, plus up to approximately 1 second eligibility and 2 seconds consumer polling.
- Productive pass 1 creates the history run. Approximately 2 seconds later, pass 2 detects the label change and publishes INBOX. UI sees it on its next 10-second poll.
- Pass 3 projects message metadata; pass 4 refreshes INBOX again, commits checkpoint and starts the next 60-second idle period. A redundant queued job may exit at the deadline guard.

Approximate visible-tab latency under healthy, light load: **minimum 1–5 seconds**, **typical 35–40 seconds**, **upper range 70–80 seconds**. These estimates assume changes are uniformly distributed in the sampling cycle, fast Gmail/DB responses and no quota/backlog. The effective counter-sampling period is about 64–68 seconds because processing surrounds the 60-second sleep. A new message requires metadata projection plus the separate 20-second message-list poll; its observed 30 seconds can simply have had a favorable phase. The implementation does not guarantee that arrivals propagate faster than reads.

Verified synthetic example of approximately **120 seconds without API failures**, using six history pages and 600 affected identities:

| Time after external read | Worker activity                                                                | INBOX unread |
| ------------------------ | ------------------------------------------------------------------------------ | ------------ |
| Immediately before t=0   | First page and initial INBOX sampled; then read occurs in synthetic Gmail      | 1            |
| t≈2–18s                  | Nine deliveries drain first page's 100 identities                              | 1            |
| t≈20/40/60/80/100s       | Stage pages 2–6, with nine drain deliveries between pages; no counter sampling | 1            |
| During last page         | External read is detected and the message's placement gets `\Seen`             | 1            |
| t≈120s                   | Finalization refreshes INBOX and commits checkpoint                            | 0            |
| t≈120–130s               | Next visible-tab REST poll updates badge                                       | 0            |

Diagnostic result: **60 additional passes, modeled 119,900 ms to the DB counter**, no error, final history ID `700`. This used the actual sync service/repository/projector and fake Date at two-second delivery spacing; it is a scheduling model, not a 120-second wall-clock benchmark. Each pass is eligible immediately; the accumulated 2-second consumer cadence causes the delay. Larger sweeps can take longer: there is **no fixed healthy-backlog upper bound**. A hidden tab or sustained errors also has no finite visible-update bound.

Additional verified conditional reproductions: a `429 Retry-After: 60` on the first INBOX request yields **121.9 seconds** from an external change near the beginning of idle; stale `labels.get` values through one sweep yield **127.9 seconds**, even after the message and checkpoint have updated. The fixtures deliberately inject those conditions; neither is established for the real incident. Google's label API defines `messagesUnread`, but does not establish a read-action-to-counter freshness SLA in that reference: [Label resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.labels).

Live evidence: current container started **18:30:44 Europe/Warsaw**; compiled worker contains the INBOX-priority and final-refresh patch. Import is complete, no pending durable work was present when inspected, and current error category was null. Sampled post-start job executions were at most **1.312 seconds**, had **zero queue retries**, and maximum interval between starts was **62.074 seconds**. The earlier 245-second gap crosses deployment/startup. Logs contain OAuth timing, but no history-page/counter-response telemetry or external-action timestamp; they cannot prove historical counter freshness or exclude a recovered service-level backoff.

4. **Smallest safe proposed fix — not implemented**

The smallest one-line improvement is a **15-second post-checkpoint idle deadline** instead of 60 seconds. It reduces quiet-account latency to roughly **15–20 seconds typical**, approximately **30 seconds at the upper edge**, but **does not fix counter starvation during draining**.

For a reliable 10–30 second target under healthy requests, make INBOX observation a small, bounded activity independent of history/inventory phase: sample an already-known INBOX when its last successful counter observation is at least **15 seconds old**, before returning from a control/drain slice, and keep idle worker eligibility at 15 seconds. Reuse/deduplicate that observation against the existing four-label sweep budget so the first-page refresh does not immediately repeat it. Preserve quota/error deadlines, authority fences, durable receipts and checkpoint rules. This also uses the startup delivery to publish a due counter instead of wasting that delivery on run setup alone. Avoid deriving a total unread badge from partially imported local messages.

If implemented, test timestamp provenance carefully: current API treats Gmail mailbox `updatedAt` as the counter observation; a dedicated observation field is safer if any other writer can advance it. No fix can guarantee freshness of a stale Gmail response or bypass an enforced quota backoff. Add bounded diagnostic fields for sweep phase, due deadline, counter observation/value, API category and pass duration to identify those cases without logging tokens or message contents.

5. **Estimated impact**

An empty sweep currently costs **7 Gmail units**: history.list 2 + labels.list 1 + four labels.get at 1 each. A 15-second idle deadline permits at most approximately four sweeps/minute: **28 units/minute**, approximately **40,320 units/day/account**, versus nominal 7/minute and 10,080/day. Actual rates are lower because processing time remains. Changed identities cost 20 units per messages.get and a changed-sweep final INBOX refresh costs 1; these existing costs remain. Faster sweeps can reduce coalescing of repeated changes. Periodic INBOX sampling during a backlog adds at most approximately **4 units/minute/account** if it is deduplicated with sweep refreshes. Costs verified against [Google's quota table](https://developers.google.com/workspace/gmail/api/reference/quota).

The default background user allowance is 2,800 units/minute; 28/minute is 1%. Default shared background daily allowance is 1.4 million: 40,320/day is 2.88% per always-active account. Multiple accounts and initial import still share project/daily ceilings.

Idle worker/OAuth acquisitions rise approximately 3–4-fold. The current implementation refreshes OAuth once per delivery, so avoid extra no-op deliveries. The global eligibility poll remains once/second. Quota ledger, catalog/counter and sync-state transactions increase approximately with sweep frequency; at one account this is tens of short transactions/minute rather than a high DB load. Independent due-INBOX sampling adds one quota reservation and one counter-publication transaction per actual additional observation, with no metadata import restart.

6. **Validation and regression tests**

Existing provider integration, unread-counter and frontend suites: **52 tests passed**. Five temporary diagnostic scenarios passed across targeted runs on disposable PostgreSQL: two-pass publication before metadata/checkpoint; stale label response; 60-second API backoff; real GmailPoller/pg-boss continuation; six-page busy history. Real queue runs exposed the counter after **6.22 seconds** and **10.31 seconds** from eligibility, including extra deadline-guard no-op deliveries in the cross-host fixture. They did not add a second mandatory minute.

Needed permanent regressions for the proposed fix:

- External read and unread after completed import; enforce due scheduling and counter publication within the intended budget without explicit `wake()`.
- Read after first-page counters during multi-page history, during 12-item draining, and during historical inventory/final reconciliation; counter must refresh before checkpoint independently of work exhaustion.
- Fresh counter visible via mailbox REST and badge while message work remains pending; metadata projection must not overwrite authoritative totals.
- Preserve cursor and durable work across counter failures, 429/Retry-After, minute/daily quota exhaustion, account revision changes and lock contention; periodic polling must not clear backoff.
- Deduplicate first-page/final/periodic INBOX requests and enforce endpoint/quota budgets; test multiple accounts and fair continuation scheduling.
- Real poller/consumer cadence and redundant queued deliveries; UI 10-second polling, visibility resume, failed HTTP retry and stale snapshot ordering.
