# Phase 2 targeted review

Reviewed commit: `66c8f6458bd2344f97ee8fccd669ed68c69d1fd7` on `codex/gmail-api-complete-provider`.

Reviewed the implementation, installed/patched pg-boss **12.33.7**, its PostgreSQL schema and transaction adapter. SQL verification used disposable PostgreSQL **18.6** containers with project migrations and independent pg-boss instances. No live databases or mailboxes were accessed. Severity below describes the original defect; all three confirmed defects are fixed in this review.

## 1. pg-boss SQL adapter

**High — stale singleton statistics could block the global selected head. Fixed.** After completion, pg-boss's cached `singletons_active` can still exclude a successor selected by admission. Its fetch returns no rows, fairness does not advance, and unrelated queues defer to that same head. Recovery depends on supervision/cache refresh; this is a confirmed delay, not demonstrated permanent job loss. The regression test seeds stale queue statistics, loads them into a fresh process, completes the predecessor, and checks successor and unrelated-account progress. The fix removes only the cached singleton veto. The installed patch's live stately exclusion, unique policy index and original locking claim remain intact; the test also rejects the successor while its predecessor is genuinely active.

**Pass — transaction and claim boundaries.** The native adapter pins one pool connection from `BEGIN` to settlement. The advisory transaction lock, selection, original `FOR UPDATE ... SKIP LOCKED`/state update, frozen priority and fairness writes all share that transaction. Concurrent-process tests reject overlapping work for one account. Injecting a persistence failure _after_ the actual claim leaves the job created, priority unchanged, retry count zero and no fairness row; the next fetch succeeds. pg-boss releases/discards the client on settlement/connection failure. Admission deferrals neither fail deliveries nor consume retries. A lost commit acknowledgement can leave an active job awaiting ordinary expiry recovery; this remains an at-least-once queue, not an exactly-once executor.

**Upgrade risk — guarded, not generally compatible.** Startup requires exactly 12.33.7. Fetch guards now reject `LIMIT 10`, changed timestamp semantics and absence of the live stately patch, instead of silently accepting/bypassing those cases. Current consumers use supported batch-one stately fetches without group/minimum-priority restrictions. Revalidate the patch, generated SQL and real-queue tests before changing version or fetch options. The snapshot argument requires **READ COMMITTED**, verified in the fixture; preserve it if changing database-role defaults.

## 2. Job selection SQL

**High — deleted-account jobs could permanently block admission. Fixed.** Account deletion leaves pg-boss jobs behind. The old unconditional fairness insert violated its account foreign key, rolling back the claim and repeatedly selecting the same head without consuming retries. A real-database regression reproduced this. Fairness now inserts only from an existing account and takes a key-share lock to protect against concurrent deletion. Stale jobs remain claimable for normal handler fencing/settlement; healthy accounts progress afterward.

**Pass — states and eligibility.** Catalog verification establishes enum order `created, retry, active, completed, cancelled, failed`; comparisons use enum ordering, not lexical ordering. Thus `state < 'active'` correctly admits created/retry only, and `< 'completed'` additionally includes active. Selection respects `blocked`, `start_after`, Gmail `next_attempt_at`, active-account exclusion and retry predecessors. Expiration recovery was exercised through real pg-boss supervision; deferred retries remain deferred while another account progresses.

**Pass — priority and fairness within the policy.** Tests cover INBOX P0 versus other-folder P1, Gmail current versus inventory P2, account rotation, reserved P0 capacity, eight-admission/60-second lower allowances and alternating P1/P2. Backfill yields to eligible current work on the same mailbox. Continuous current work can intentionally defer that mailbox's backfill; this is not unconditional starvation freedom. No additional permanent filtering block was found under healthy supervision and supported consumers. Discovery's test now permits arbitrary completion order among concurrently scheduled P1 folders while still requiring INBOX first.

## 3. Performance and connections

**Medium — quadratic backlog filtering serialized admission. Fixed.** With 50 accounts, 5050 due jobs (including 1667 backfills) and 20,000 terminal jobs, `EXPLAIN (ANALYZE, BUFFERS)` showed the candidate CTE scanned 1667 times: **1318–1496 ms** per selection in a three-sample baseline. The equivalent null-safe distinct current-mailbox set reduced this to one scan and **88–129 ms** in an isolated post-fix run. A regression checks repeated scan counts, avoiding fragile timing thresholds. The ready-job index is used. These are local warm-cache measurements, not production throughput guarantees; remaining joins, sorting and active/retry scans still grow with backlog. Monitor admission latency and retained rows before increasing scale.

**Medium — conditional connection exhaustion risk remains.** Each worker has an application pool (default 10) plus pg-boss's separate pool (default 10). Each successful IMAP IDLE account lease holds an additional dedicated PostgreSQL session globally; each concurrent Gmail authority operation opens another dedicated session. These are outside `DATABASE_POOL_SIZE`. Lease contention/loss tests verify exclusion and cleanup, but startup/reconnect contenders add transient connections. Budget approximately `workers × (application pool + boss pool) + IDLE accounts + concurrent Gmail authority + web/enqueue/admin connections`, with headroom. Pools grow on demand. A server configured for 100 connections can exhaust that budget with two workers and around 60 IDLE accounts even before web/admin demand; no live exhaustion was tested. Size the server and deployment accordingly; no new connection-management design was introduced.

**Operational limits.** Mailbox authority reserves an application-pool slot while service queries need further slots: very small pools, or enough simultaneous command/lock holders, can stall work (pre-existing behavior). Keep spare application slots. Default synchronization consumers provide 13 polling threads per worker, so mismatched queues can repeatedly perform selection; the try-lock avoids waiting contenders but is not a global query-rate limit. Queue expiry can also precede handler termination: admission counts queue-active rows, not surviving remote operations. Existing mailbox/Gmail authority provides conflict protection, but Phase 3 must not treat this count as a hard remote-operation cap.

Type checking and ESLint passed; changed-file formatting and diff checks passed. Regression tests reproduced the two blocking bugs and the repeated-scan defect before their fixes; rollback verification runs against actual pg-boss.
