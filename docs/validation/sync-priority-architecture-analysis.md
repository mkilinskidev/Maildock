# Cross-provider synchronization priority analysis

Date: 2026-10-10. Source baseline: `5efc23c9cedc3a0ec41c77c10b29b9dcbf4f3f8f`.

This is source analysis and an implementation proposal, not a runtime benchmark. The existing [Gmail latency diagnosis](gmail-read-status-latency-diagnosis.md) is the baseline; its experiments and deployment observations were not repeated. Production code, intervals, databases, imports and mailbox contents were not changed. No tests, commits, pushes or ADR creation were performed. Configuration values below are code defaults, not verified deployment settings.

**Conclusion:** native Gmail, Microsoft OAuth2 IMAP and password IMAP do not currently guarantee P0 INBOX precedence. There are useful safeguards to retain: Gmail account authority and durable history receipts; IMAP mailbox authority, IDLE wake-ups and bounded backfill ranges. None supplies a complete cross-account priority/fairness or coherent message/counter publication contract.

### Actual ordering, concurrency and recovery

Evidence: [worker composition](../../src/composition/worker.ts), [worker registration](../../src/composition/worker-process.ts), [JobRuntime](../../src/modules/jobs/infrastructure/job-runtime.ts), [configuration](../../src/shared/infrastructure/config/config.ts).

Gmail registers two local consumers; IMAP recent and delta each register `messageSyncConcurrency` consumers (default two **per queue**); backfill registers one; discovery uses `workerConcurrency` (default five). These are independent capacities, not one global worker limit. Multiple worker processes multiply local capacity. pg-boss supplies queue singleton behavior, not a shared provider/account receive budget. DB pools and remote connection limits are shared practical bottlenecks; `DATABASE_POOL_SIZE` defaults to 10 for the application worker database.

The installed pg-boss 12.33.7 `dist/plans.js` fetch SQL selects a queue's eligible jobs by priority descending, then creation time, with locking; `dist/manager.js` defaults to batch size one. Equal creation timestamps have no application-level deterministic tie order. A priority of -10 in backfill cannot make a different queue's delta consumer preempt it. Already active jobs are not preempted by pg-boss. The baseline's approximately 2-second consumer polling remains applicable.

The [Gmail account lock](../../src/modules/mail/infrastructure/gmail-account-lock.ts) serializes native synchronization and native commands on a reserved session. The [IMAP mailbox lock](../../src/modules/mail/infrastructure/mailbox-lock.ts), `createMailboxLock`, serializes recent/delta/backfill and command execution for one mailbox, not an entire account. Both use try-locks: conflict throws, rather than establishing a priority-ordered waiting list. Different IMAP folders from one account can run concurrently and occupy several consumers/connections. No explicit fair-share admission is present across receive transports.

[Delta enqueue](../../src/modules/mail/infrastructure/delta-sync-jobs.ts) and [backfill enqueue](../../src/modules/mail/infrastructure/backfill-sync-jobs.ts) use [enqueueCoalescedSync](../../src/modules/mail/infrastructure/coalesced-sync-job.ts): one pending created/retry delivery per key, protected by a producer transaction lock. It preserves an existing retry deadline; IDLE does not automatically bypass a pending failed delivery. Backfill keys include the frontier, so coalescing alone is not mailbox-wide exclusion; the execution lock remains essential. Gmail uses account singleton keys and persisted `next_attempt_at`; enqueue/wake clears a normal idle deadline but preserves an error deadline.

Delta/recent/backfill queues have four retries, initial retry delay 30 seconds, exponential backoff capped at 900 seconds, and expiry 900 seconds. Discovery uses 15-second initial delay and 120-second expiry. Gmail queue expiry is 180 seconds with the same four/30/900 retry policy; handled Gmail API failures instead persist service deadlines (at least 30 seconds, or 300 seconds for authentication/access/API-disabled categories). A lock collision can therefore delay urgent work via queue retry. Readiness supervision pauses all business workers until instance readiness is satisfied; latency targets exclude that state.

### IMAP transport and capability differences

[AccountsService.getProviderImapAccountForWork/resolveCredential](../../src/modules/accounts/application/accounts-service.ts) resolves a password or OAuth2 token into the same `ProviderImapAccount`. [imapOptions](../../src/modules/accounts/infrastructure/imap-smtp-mail-provider.ts) changes the authentication field, not the sync engine. [MicrosoftOAuthProvider.accessToken](../../src/modules/accounts/infrastructure/microsoft-oauth.ts) adds MSAL token/cache acquisition under a row lock and possible authorization failures. There is no Microsoft Graph receive path here.

[ImapSmtpMailProvider](../../src/modules/accounts/infrastructure/imap-smtp-mail-provider.ts), `listMailboxes`, `synchronizeRecentMailbox`, `synchronizeDeltaMailboxImpl`, `synchronizeBackfillMailbox`:

- Discovery obtains folder status and capabilities; `MailboxService.listForAccount` sorts paths alphabetically, and `MailboxDiscoveryService.run` schedules all selectable folders with `Promise.allSettled`. Neither supplies INBOX-first execution.
- Recent synchronization searches the complete recent window and fetches every batch in one invocation. `MessageService.runRecentSync` declares success afterward and schedules backfill. Delta polling and IDLE eligibility both require recent success. An INBOX still importing its recent window has no normal delta/IDLE receive path.
- Delta selects one mailbox read-only on a fresh connection. It loads all local placement UIDs, fetches all new UID batches, then flags. With CONDSTORE and a baseline it uses `changedSince`; without one it fetches flags for every local UID. Presence SEARCH runs over local UIDs even with CONDSTORE, then independently confirms absence before deletion. STATUS validates epoch/counters; only then do removal and completion callbacks run.
- Metadata/UID progress and flag/removal batches commit incrementally. The persisted MODSEQ is SELECT's earlier value, intentionally allowing replay of concurrent changes rather than skipping them. UIDVALIDITY changes invalidate placements/cursors, request recent sync and return; ordinary failures preserve retryable progress and rethrow.
- IDLE manager refreshes eligible watches every 60 seconds. It listens to exists/flags/expunge/mailboxClose, reconnects with 1-second exponential base capped at 5 minutes plus up to 50% jitter, and queues delta on reconnect. It uses a separate watch connection, automatic IDLE, 4-minute renewal and 6-minute socket timeout. Sync connections use 10-second connection/greeting and 15-second socket timeouts; these are not total whole-job duration bounds.

IDLE/CONDSTORE behavior is capability-dependent, not guaranteed by Microsoft authentication. No live server capability, connection-limit or account-count assumptions were made.

## C. Proposed P0/P1/P2 policy

### Shared contract and fair admission

P0 comprises current INBOX arrivals, flags, deletions, archive/move membership changes, metadata and corresponding counters. An old message changed now is P0 if it affects INBOX; message age alone does not determine urgency. A move out of INBOX remains P0 even after its current INBOX membership is gone. P1 covers current changes elsewhere; P2 covers historical inventory and non-urgent reconciliation. Discovery/epoch repair needed to make INBOX usable is a P0 prerequisite; background catalog refresh is maintenance. Lazy body/attachment work retains its separate interactive policy.

At each safe boundary select due, unblocked P0 before admitting another P1/P2 slice to shared receiving capacity. Reserve P0 capacity so already running P1 work cannot occupy all delta consumers. Across eligible accounts use round-robin/oldest-last-served order, at most one outstanding P0 slice per account. Apply an aggregate IMAP account connection/work ceiling across folders and worker processes; count watchers when sizing remote connection capacity. Gmail retains account serialization. Provider queue capacities remain distinct, with explicit headroom for shared DB/project resources.

Strict P0-only admission under endless P0 traffic conflicts with starvation prevention. Proposed exception: a small reserved lower-priority service budget, one P1/P2 slice after eight productive P0 slices or 60 seconds of eligible waiting, whichever occurs first, while retaining P0 capacity. Rotate waiting P1 and P2 work/accounts; do not spend every maintenance turn on P1. These are proposed tuning values requiring approval, not existing guarantees. No progress guarantee is possible without enough resource headroom or while provider backoff blocks the account.

Safe preemption means finish a fetched batch, commit projection and its progress receipt, release the authority/connection, then reevaluate due work. Never interrupt an IMAP FETCH iterator mid-response, advance a cursor over unpersisted work, hold a DB transaction across HTTP, or kill a lock owner just to admit P0. A request timeout can consume the latency budget; slice count/time budgets are cooperative, not hard remote deadlines. Preserve account revision, lock-session and UIDVALIDITY fences.

Retry deadlines override priority. A poll/IDLE/wake must not erase provider backoff. Prefer a short coalesced reschedule for known lock contention rather than treating it like a remote network failure, without busy looping. Reserve part of existing Gmail **background** allowance for P0, retaining the 70% background ceiling and interactive headroom; P2 is admitted only from the remainder. Fairly divide the shared project allowance between accounts. Release authority/resources during quota waits and publish a blocked/stale status.

### Gmail: priority without weakening account history

Keep unfiltered account-wide history as the authority for the global checkpoint. Google's [history contract](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list) describes ordered history, paging, an optional label filter and expired-cursor recovery; it does not make a filtered result sufficient for a complete account checkpoint. The current [ADR 0014 proposal](../adr/0014-gmail-account-history-and-progressive-sync.md) already preserves this invariant.

Retain event label IDs and message-reference label hints in decoding. At intake classify INBOX label additions/removals, events for existing local INBOX placements, and new-message hints. Unknown IDs must remain eligible for prompt classification rather than silently becoming P1. Deduplicate by native message identity and promote existing work without losing receipts. Read/unread label events affecting known INBOX messages are P0; removals/deletions remain P0 via previous membership. Use deterministic priority plus age/identity ordering within durable work. Fetch full current state and reuse `projectGmailBatch` label semantics, pending-command overlays and per-message history guards; do not replay individual label deltas as authoritative final membership.

**Reordering already staged identities is safe in principle** because projection is current-state and idempotent, provided every identity is still accounted for, successful projection and completion remain atomic, and the global checkpoint advances only after all original pages/fragments/work complete. Retain fixed sweep start, page-token/digest guards, fragment bounds, run/revision fencing and expired-history re-enumeration. Do not mutate fragment ordering during resume without preserving a stable ID sequence/digest contract. Priority metadata must survive deduplication and retries.

This improves known work but does not find P0 events hidden behind later history pages. First adapt existing history intake to stage additional bounded pages/fragments while P1 work is outstanding, with a durable outstanding-work ceiling and fair draining. That needs an explicit change to the current drain-before-next-page rule; pagination can progress only once the fragment is durably staged. Do not promise 30 seconds for arbitrary account-wide history backlog.

For an INBOX freshness target during very large backlogs, a bounded **message reconciliation** path is additionally needed: discover recent/current INBOX identities and refresh tracked INBOX identities for flags/removal, under the same account authority and quota. It must cover identities that disappeared from INBOX, use durable progress, and never advance the global checkpoint or mark account inventory complete. A listing of current INBOX IDs alone misses archived/deleted identities; a label-filtered history shortcut is not approved as complete removal coverage. Reuse inventory/projector primitives, but explicitly add receipt/run support and evidence for coverage before implementing this path. Its cost grows with tracked INBOX size; this is an optional targeted phase, not a free optimization or universal bounded SLA.

Initial bootstrap should materialize the current INBOX working window before other recent labels, then permit current catch-up while remaining recent/history inventory proceeds as P1/P2. Existing account-wide recent completion must not become a gate on every P0 observation. History-expiry recovery keeps a new baseline and incomplete coverage until reconciliation/catch-up finish; preserve canonical message identities and cached content.

### IMAP: prioritize and yield existing work

Classify INBOX consistently using the canonical INBOX path (case-insensitive), aligned with IDLE and All Inboxes. Sort INBOX first at discovery and enqueue, but enforce it at consumer admission as well. Give recent-INBOX initialization a reserved opportunity; introduce a resumable recent-window cursor so a large folder does not monopolize a consumer. Mark the current working window usable separately from complete recent import, with UIDVALIDITY and a safe arrival frontier; enable P0 only after that frontier is valid.

Split whole delta runs at fully consumed FETCH/persistence boundaries. Persist new-UID progress and reconciliation cursors; retain the original MODSEQ baseline until the required flag/presence sweep finishes. On resume revalidate epoch and authority. Process INBOX new/current work before historical reconciliation; revisit arrivals between reconciliation slices. Presence checks/removals are current work when they affect INBOX, even if the affected message is old. Defer their bulk scanning cost without dropping correctness or falsely declaring counters coherent.

Keep bounded backfill and its repair poller. Add account/global admission checks, plus due-P0 checks at chunk boundaries; avoid repeatedly launching a same-mailbox chunk just before P0 becomes eligible. CONDSTORE accelerates flags but does not eliminate the current presence scan. Neither password nor Microsoft OAuth needs a separate implementation.

### Publish related UI state coherently

Keep **observed remote totals**, **locally materialized totals/unread**, and **coverage/freshness** distinct. Gmail remote totals can legitimately include historical messages not imported locally; IMAP recent-only imports also have incomplete local coverage. A remote unread total of two and zero imported rows must be shown as incomplete remote coverage, not presented as two available synchronized messages. A 50-row page or conversation list is not a total-count authority. Google's [label resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.labels) defines message totals, but provides no atomic pairing with message GET responses or read-change freshness bound.

Proposed minimal contract: keep raw counter observations as internal samples until the required current INBOX projection scope is resolved. Publish a mailbox generation, dedicated observation timestamp, coverage state and its visible counter fields together in a short fenced final transaction after bounded message batches. The local visible unread value should describe materialized placements; remote totals remain explicitly labeled during partial coverage. Advancing the INBOX publication generation does not require historical backfill or unrelated P1 work to finish, and does not advance Gmail's global history checkpoint.

A generation marker alone does **not** hide partially committed message batches. Serve related mailbox/message data in one short repeatable-read snapshot/envelope and label an in-progress observation as such; recompute the materialized counter within that snapshot if intermediate rows are exposed. If product requirements demand retaining the entire previous message snapshot until completion, versioned/staged projections are required and materially increase scope. That stronger contract should be separately approved. Remote changes between FETCH and STATUS/labels.get may still need another pass; never claim a provider-atomic remote snapshot from local transactions.

Replace independent mailbox/message state application with one visible-tab refresh coordinator for selected mailbox, related counters, selected metadata and All Inboxes. Prefer a small combined DB snapshot endpoint; if using multiple endpoints, include generations and retry mismatched results before applying them together. Batch React updates only after the related responses succeed; reject old requests by request generation and selection identity. All Inboxes needs a per-account publication vector, not a global remote checkpoint. Its counts must match the same enabled/selectable/active scope as its rows.

Invalidate/update ready-reader flags and membership on a new publication, preserve lazy content caching, and invalidate loaded tail rows/cursors after removals or moves. Retain optimistic local-command adjustments but reconcile them using dedicated observation/publication provenance. Hidden tabs resume coherently; HTTP failure retains the previous coherent envelope and marks freshness, rather than updating just its badge.

**Assessment of the previous 15-second proposal:** shorter post-checkpoint eligibility is still a useful later tuning change; source diagnosis remains valid. Independent periodic `labels.get(INBOX)` publication is unsuitable as the primary fix under this requirement. It may collect a candidate observation but cannot announce coherent completion ahead of message work. Fifteen seconds plus current independent 20-second message polling can already exceed 30 seconds before backlog/HTTP costs; coordinate UI refresh as part of the target. The baseline estimates an empty sweep at seven quota units and roughly 28/minute at four sweeps/minute; current [quota costs](https://developers.google.com/workspace/gmail/api/reference/quota) remain consistent with that estimate. Metadata/reconciliation cost and reduced coalescing dominate under load; measure them before adopting the interval.

## E. Measurable acceptance criteria

The following are future tests, not executed results. Use synthetic providers and disposable PostgreSQL/pg-boss for deterministic scheduling/recovery, plus controlled browser fixtures. Record external change time, detection, projection commit, coherent publication and browser application separately. Any live-mailbox validation requires separate authorization.

Proposed healthy-load objective: visible-tab INBOX publication **p95 at most 30 seconds**, typically 10–30 seconds, for a declared small-change workload. Fix and report account count, backlog size, local INBOX size, HTTP/IMAP response latency, worker/pool capacity and IDLE availability before interpreting that objective. A useful reference fixture is three enabled accounts, one external change/account/cycle, fast sub-second provider responses, metadata-only sync and sustained historical import. Also sweep beyond the nominal account count (including over 20 Gmail accounts) to discover the capacity envelope.

Guarantees should be structural: persisted work survives retries, checkpoints are safe, P0 receives the next eligible scheduling opportunity, and presented related state has explicit coverage. Ten–30 seconds is an SLO for a measured operating envelope, not a universal guarantee. Current default no-IDLE IMAP polling (300 seconds) cannot satisfy it; even minimum configured polling (30 seconds) leaves no 30-second budget for processing/UI. Reconnect backoff, account/project quota exhaustion, hidden tabs, server inconsistency, large sweeps and unavailable capacity suspend the target and must expose freshness/blocked status.

## F. Architectural decisions and approval before implementation

An ADR is warranted because priority/fairness, partial-import counts and publication coherence form a user-visible contract across transports. Create it only after review; none is created here. It should relate to ADR 0008 (recent/history storage policy) and proposed ADR 0014 (account-wide Gmail authority), distinguish this report's operational P0/P1/P2 from similarly named roadmap phases, and record:

1. P0 definition including old-message changes and INBOX removals, safe yield boundaries, reserved capacity, cross-process account fairness and the bounded maintenance exception.
2. Visible materialized counts versus separately labeled remote totals, working-window coverage and freshness; whether partial progress is visible or whole-observation staging is required.
3. Publication generation/snapshot endpoint, frontend/All Inboxes request ordering, ready-reader and paginated-row invalidation.
4. Gmail unfiltered checkpoint invariant, durable priority intake, unknown-event classification and conditions/cost ceiling for optional INBOX reconciliation. No filtered checkpoint substitution.
5. IMAP resumable progress/epoch/MODSEQ semantics, capability-dependent target and reconnect/fallback behavior; Microsoft OAuth remains an authentication variant.
6. Approved capacity envelope, latency SLO, polling interval/API budget changes and behavior during quota/error deadlines. Gmail Push/Pub/Sub remains deferred.

The earlier Gmail diagnosis remains valid as a latency diagnosis. Its independent counter-refresh recommendation and counter-first regression acceptance are superseded here by coherent message/counter scope and explicit partial coverage. Approve the count-display contract, fair-service exception/capacity limits, polling cost and any supplemental Gmail reconciliation before implementation; source-only analysis does not authorize those production changes.
