# F8: authentication and MFA throttling discovery

Reviewed 2026-10-06 against commit `f4604724d884d4cd0926ec29411df1830ae1fb25`. **F8 remains OPEN.** This is discovery, not an implementation. F2 remains closed; no application code, migration, dependency, configuration, or existing test was changed. No commit or push was made.

The principal gaps are unthrottled authenticated management proofs, non-atomic password-backoff admission, and insufficient aggregate admission before expensive authentication work. Anonymous MFA's existing five-attempt challenge budget, ten-failure account lock, and recovery single-use controls worked in real PostgreSQL tests.

## A. Entry-point matrix

`M` means the entire operation joins PostgreSQL advisory transaction lock **1296125023**, at READ COMMITTED, before authority/factor/password reads. Serialization prevents simultaneous credential work but is not a rate limit. `Owner pending` means a valid immutable-owner session on a not-yet-READY instance. All explicit MFA mutations enforce exact Origin, JSON, strict schema, 4096 streamed bytes, and a 10-second body deadline through `initialMfaHttp`.

The catch-all exports **GET and POST only**. It suffix-allows GET `get-session`, POST `sign-in/username` and `sign-out`; all other dispatched operations return 404 before reaching Better Auth. The username and session handlers still require the corresponding Better Auth router path: a suffix match is not itself a new registered endpoint. POST `get-session` is blocked even though Better Auth supports it internally. Trailing slash normalization inside the factory does not expand the catch-all's suffix allowlist.

Other application routes/pages use `getValidOwnerSession`/`getValidBusinessSession` via server API. Their reads can refresh an already-valid session but cannot verify a password, create a login challenge, or consume MFA proof. These internal refreshes do not consume L1. Login/setup/enrollment/replacement pages render/navigation only; their mutations are the operations above. No additional owner credential verifier was found in `src`.

Mail-account IMAP/SMTP credentials and provider settings are business operations protected by an already-READY owner session; they do not authenticate the owner to Maildock. This review inventories mail OAuth navigation/proofs above to distinguish them from blocked Better Auth social-login routes, but does not redefine F8 as a remote-mail-provider authentication audit.

## C. Better Auth 1.7.5 findings confirmed from installed source

1. `dist/api/index.mjs` invokes `onRequestRateLimit` in the HTTP router's `onRequest`. `auth.api` endpoint invocation does not traverse that router. `dist/api/rate-limiter/index.mjs` consumes the database budget before endpoint work, uses custom-rule precedence over plugin/core rules, and sends **`X-Retry-After`** on 429. Maildock L2/setup use standard `Retry-After` instead.
2. `dist/plugins/username/index.mjs` validates actual username length/grammar before lookup; Maildock allows ASCII letters/digits/dot/underscore/hyphen, 3–64 characters. Lookup lowercases, but login does not trim. Invalid syntax yields 422 without dummy hashing; valid unknown username performs **real password hashing** to reduce enumeration. Its password schema is plain `z.string()`; `emailAndPassword.maxPasswordLength=128` does not impose that bound on this plugin sign-in.
3. `dist/plugins/two-factor/index.mjs` removes the temporary password session, creates fresh challenge plus count=0 companion records, and returns 2xx with `twoFactorRedirect`. It does not reset account failures on password success. New challenges do not delete all prior challenges.
4. `dist/plugins/two-factor/verify-two-factor.mjs` branches on an active session. Anonymous branch consumes/rearms the challenge tracker; authenticated branch has no-op attempt functions. `totp/index.mjs` and `backup-codes/index.mjs` run account locking/failure/reset **only when `isSignIn = !session.session`**. This is why authenticated management needs its own limiter.
5. Recovery verification decrypts the encrypted list, checks exact code inclusion, then calls `incrementOne` with both factor ID and previous `backupCodes` value before storing the reduced list. The resolved Drizzle patch repeats conditional guards in the outer UPDATE after PostgreSQL lock waits. Existing tests prove one CAS winner and no budget over-admission. This patch is installed, not just present in `patches`.
6. Anonymous MFA errors obtained with `asResponse:true` are normal responses inside Maildock M and **commit** attempts. Management/initial-MFA direct API errors are thrown and roll back their transaction. Initial enrollment's independent L5 admission survives that rollback; management has no corresponding reservation to survive it.
7. The account-lock increment alone is not a pre-verification reservation. Safety of Maildock's ten-proof ceiling relies on M around the account precheck and crypto operation; do not remove M based solely on an atomic increment.
8. `@better-auth/core/dist/utils/ip.mjs` supplies the request identity behavior in section F; `dist/env/env-impl.mjs` caches `NODE_ENV` when loaded. Changing `process.env.NODE_ENV` mid-test is insufficient to characterize production.

## E. Concurrency results

F8 fixtures create three independent postgres-js pools: primary application DB/Auth, second application DB/Auth, and control/observer DB. M races hold `pg_advisory_xact_lock(1296125023)` on the control transaction, launch the first operation, observe an actual ungranted advisory lock in `pg_locks`, launch the second, observe both waiters, then release. Polling observes PostgreSQL state; elapsed time is only a timeout safeguard, not the ordering assertion.

- **Password gap (F8-04):** both HTTP route calls reach M before either failure exists, because the username backoff SELECT occurs before M. Release permits two real password verifications despite the first failure's delay. Different client addresses demonstrate the independent IP-bucket limitation. These calls use the same route composition/pool with separate DB transactions; account/factor races additionally use independent pools.
- **Account ceiling (F8-07/F8-13):** two pools attempt different challenges at nine failures. M admits one crypto verification, commits count=10/lock, and the next sees 429. Concurrent challenge creation produces two five-attempt trackers but does not multiply account budget.
- **Challenge ceiling (F8-08):** at count four, one pool records fifth failure; the other invalidates the exhausted challenge without checking another proof.
- **Replacement ceiling (F8-12):** at count four, one failed confirmation commits fifth; the second observes exhaustion; persisted count never reaches six.
- **Setup reservation (F8-18):** control holds the existing `rate_limit` row FOR UPDATE; both independent UPSERT statements are observed waiting in `pg_stat_activity` before release. Exactly one reservation is permitted at max-1.
- **Underlying rate-limit/recovery CAS:** existing increment-one tests use row-lock barriers and 20 actual writers. Recovery login and management proof races additionally exercise full Maildock ceremonies, not just adapter statements. Existing F2.3 four-challenge recovery race produces 200/401/401/401 and one session; management/regeneration reuse similarly has one winner.
- **No-proof requests (F8-19):** both independent calls without challenge authority still reach M. This proves lock/DB admission is not protected by proof counters; it does not measure or claim a demonstrated service outage.

All tests use disposable migrated PostgreSQL. Expiry tests move the isolated persisted deadlines/timestamps into the past instead of waiting for production-sized windows. ## F. Proxy/request identity observations (F8 only)

Maildock does not configure `advanced.ipAddress.ipAddressHeaders`, `trustedProxies`, or `disableIpTracking`. The installed default header list is **only `x-forwarded-for`**. It does not use the socket peer from a Web Request, `Forwarded`, or `X-Real-IP` by default. Without configured trusted proxies, a valid **single address** is accepted; a multi-address comma chain is rejected. The helper can strip configured trusted proxies from the right, but Maildock has no such configuration. IPv4-mapped IPv6 normalizes to IPv4; IPv6 buckets default to /64.

In production an unresolved address becomes one shared **per-path** `no-trusted-ip` bucket, not a disabled limiter. In tests/development it becomes `127.0.0.1`. `MAILDOCK_ENV` controls Maildock cookies/configuration; Better Auth's environment helper uses module-load `NODE_ENV`/`TEST`.

Consequences established by F8 evidence:

- Changing single XFF changes L1's bucket in the current composition; changing XFF does **not** change L2's canonical username bucket or L6/L7/L8.
- If deployment forwards attacker-supplied single XFF, IP limits can be partitioned arbitrarily. If the proxy appends a chain rather than replacing/normalizing it, default resolution can fall back to a shared bucket. If ingress removes all accepted headers, all public clients share a per-path bucket and can consume each other's quota.
- Even perfect proxy trust cannot make a per-IP budget an aggregate/owner budget: independent real clients still get independent expensive-work buckets.
- `src/proxy.ts` copies incoming headers to Next; it adds CSP but no trusted-address sanitation. `docker-compose.yml` does not include a reverse proxy; actual public ingress configuration was not supplied or tested.

**F9 owns deployment trust, proxy/header sanitation, and ingress reachability.** F8 must not rely on a presumed deployment boundary to compensate for missing application admission. No F9 fix was made and no current VPS exploitability is asserted.

## G. F8 findings

### F8-G1 — HIGH: authenticated management proof verification is unbounded

- **Entry points:** recovery regeneration and authenticator-replacement start, both proof types.
- **Exact cause:** `mfa-management.ts:authorize` directly verifies the password without L2/L4/L5; its server `verifyTOTP`/`verifyBackupCode` calls bypass L1. Better Auth's authenticated branch skips L6 and L7. No Maildock management counter exists. Failed authorization throws, so the enclosing transaction rolls back rather than reserving any durable admission.
- **Consequence:** a holder of an active owner session can make unlimited online password guesses and, after knowing the password, unlimited TOTP/recovery guesses during session validity. The password + factor reauthentication intended for high-impact recovery regeneration/replacement has no verification budget. Valid Origin is not a secret and does not prevent a session holder from making these requests. This is not an anonymous MFA bypass.
- **Evidence:** F8-10 actual HTTP route functions: 11 incorrect passwords and 11 incorrect mixed factor proofs all 403; zero attempt changes in every potential limiter store. Installed source explicitly gates account checks with `isSignIn`.
- **Minimal direction:** introduce a shared persistent **owner-scoped management/password-proof admission** before Argon2 and a bounded factor-proof budget shared across regeneration/replacement start and proof types. Ensure expected failure counters commit. Preserve atomic recovery consumption and all existing management authorization/state checks.

### F8-G2 — MEDIUM: canonical username backoff does not atomically control admission

- **Entry point:** username password login.
- **Exact cause:** catch-all calls `getLoginDelaySeconds` before entering the factory's M transaction and records failure only after that transaction resolves. Atomic failure UPSERT does not make this SELECT/admit sequence atomic. Different IP buckets remain independent.
- **Consequence:** a pre-admitted batch can continue checking passwords after a failure should impose account delay. M limits simultaneous Argon2 work to one, but does not reject an already-queued batch; this also queues work ahead of legitimate MFA operations.
- **Evidence:** F8-04 PostgreSQL barrier forces both requests through the precheck before release; both return wrong-password 401, count=2, while a subsequent request is correctly throttled. No timing-only race assertion.
- **Minimal direction:** move/repeat canonical account admission within the same DB serialization boundary as password verification or use an atomic persisted admission reservation. Commit expected failures before releasing authority; retain independent request/aggregate budget before waiting for M. Do not merely make the existing failure increment atomic again.

### F8-G3 — MEDIUM: aggregate unauthenticated admission is missing before expensive work

- **Entry points:** username login; public MFA TOTP/recovery/cancel wrappers; replacement resume/complete authority checks. The strongest demonstrated expensive-work case is valid unknown usernames on login. Initial enrollment already has L3/L5 admission and is not included in this gap.
- **Exact cause:** login has per-submitted-username L2 and per-IP/path L1, with no instance-wide hash/admission budget; valid unknown users perform Argon2 hashing. Explicit MFA routes call server API and have no HTTP request limiter at all. L6/L7 require valid challenge/account and do not bound missing-proof lookups or M waiting. M is a blocking concurrency gate rather than bounded request admission.
- **Consequence:** independent clients or spoofable XFF can repeatedly submit new valid unknown names to create real hash jobs and persistent backoff rows. Missing-challenge MFA requests can queue the global auth boundary without spending any verification counter. There is no application aggregate bound on these paths. Tests prove admission/cost paths, not a service-outage threshold; no stress testing was performed.
- **Evidence:** F8-05 admits 11 dummy hashes with distinct names/addresses; installed plugin contains the real hash call. F8-15 confirms explicit wrapper calls do not consume plugin HTTP buckets. F8-19 observes no-proof requests waiting at M with no counters.
- **Minimal direction:** add small atomic PostgreSQL request/work admission **before** expensive hashing and before waiting for the global boundary. Scope expensive login work globally for this single-owner service as well as retaining canonical owner and client controls. Give explicit public MFA routes request admission without replacing their correct proof budgets. Define cleanup/bounds for attacker-selected username rows. Do not redesign the already-fixed setup admission.

### F8-G4 — LOW: sign-in lacks explicit bounded input before limiter lookup

- **Entry point:** username sign-in.
- **Exact cause:** catch-all calls unbounded `request.clone().json()` to extract username before L1 and L2 decisions. Unlike `initialMfaHttp`/setup it has no streamed size/deadline limit. Installed username password schema has no length maximum; the email-password configuration's 128 limit does not bound this plugin verifier/dummy hash path.
- **Consequence:** application parsing/retained input work precedes admission; oversized password/body input reaches the expensive verifier/hash path. No universal proxy/Next transport limit was established in this route-function review. This is a concrete application-level inconsistency, not a claim that the public deployment accepts infinite bytes.
- **Evidence:** F8-20 >8KiB JSON and 129-character password produce credential 401 after the unknown-user hash path, rather than bounded input rejection; source proves clone parsing precedes both limit checks.
- **Minimal direction:** use bounded streamed login input/deadline and explicit login password maximum before expensive work, while preserving the existing username grammar/case behavior. Avoid silently assuming signup configuration bounds sign-in.

### INFORMATIONAL observations; no additional vulnerability demonstrated

- Password-stage success resets **password** backoff before MFA, but it does not reset **MFA account** failures. F8-06/F8-14 disprove a fresh-challenge MFA budget refund. Keep counters separate unless a later explicit product policy changes them.
- L7 is stored on the single factor row rather than a separate owner-attempt table. Correct replacement requires old password + factor and revokes previous authority. No cheap anonymous factor-recreation/reset path exists.
- Account-scoped lockouts inherently permit someone who already knows the password to spend the owner's MFA budget. This tradeoff is not an extra defect proven here; do not remove account protection to avoid lockout.
- Bad/missing bootstrap uses the shared setup invalid bucket even during initial enrollment. Authorized buckets remain separate. No path from invalid secrets to setup Argon2 was found.
- Better Auth's `X-Retry-After` differs from Maildock's `Retry-After`; standardizing client retry handling is inexpensive but does not close the core gaps.
- No **BLOCKER** was demonstrated; HIGH/MEDIUM gaps still require closing before declaring F8 complete.

## H. Existing controls that are correct and should be retained

- Immutable single-owner binding, route allowlist, strict Origin/JSON/body boundaries on explicit MFA routes, READY gating, no public MFA disable or generic management endpoints.
- F3 setup authorization before hashing, independently committed 5/60 reservation, global **nonblocking** one-job setup gate, and initialized-state recheck. No regression observed.
- Initial MFA's shared, persisted 5/60 start/resume/complete limit; failed passwords/codes cannot refund it by transaction rollback.
- Anonymous TOTP/recovery's common five-failure challenge and ten-failure account budgets, including expiry, mixed methods, fresh challenges, password-stage success, concurrent calls and independent Auth instances.
- Returning anonymous MFA failure responses inside M so Better Auth attempt writes commit; challenge-only cookie filtering prevents selecting the weaker authenticated verification branch.
- Global MFA transaction boundary across password login/session creation, enrollment, login factor verification, management and replacement. Keep it when adding admission; it preserves the observed account ceiling and single-use proofs.
- Resolved patched Drizzle guarded UPDATE, database rate-limit max-1 behavior, recovery-code CAS, single-use challenge consume, and management/login recovery reuse guarantees.
- Replacement's persisted five-attempt **ceremony-wide** budget and 600s authority, exact factor binding, no resurrection of old factor/session, and no session returned by confirmation. Resume cannot reset that budget.
- Bounded session lifetime/revocation and commit-failure rollback with no plaintext recovery-code or authority leakage.

## I. Proposed implementation scope for a later session

### MUST FIX for V1

1. Add one coherent PostgreSQL-backed admission layer for authentication work: canonical owner/password admission and shared management proof budgets. Place account admission inside the credential serialization boundary or reserve atomically, and preserve committed failure counts even when verification rejects.
2. Add aggregate request/work admission before password hashing and before blocking on M, including actual Maildock MFA wrappers. Keep existing IP limiting as an additional control and retain the proven L6/L7/L8 budgets; fresh challenges must continue sharing account state.
3. Bound login stream size/read time and password length before costly processing, using the already established explicit-route style. Bound/expire attacker-generated username counter state as part of the admission design.
4. Validate these changes against the small F8 cases and existing real PostgreSQL races, including independent pools, max-1 admission, commit versus rollback behavior, and recovery reuse. Do not replace working MFA/setup/session ceremonies with a new design.
