# Architecture review against real Dovecot evidence

2026-10-12. Read all five Thunderbird research documents, the architecture and validation proposal, Phase 1 results/implications, and Phase 1B results/decisions. Reviewed and reused the actual experimental transport mechanisms, without modifying those files or importing production receiving services. [Measurements](BENCHMARK_RESULTS.md) and [setup](SETUP.md) delimit what was tested.

## Full inventory versus progressive windows

The measured source-inspired baseline gives first 128 metadata records after 1.57–2.12 seconds, versus 216–304 ms for progressive windows. Baseline maximum event-loop delay is 1.39–1.87 seconds versus 44–51 ms. Baseline peak RSS is 243–266 MiB versus about 224–225 MiB; both include the 50k in-memory store and ground-truth oracle. Complete times overlap: 7.09–7.91 versus 6.18–8.12 seconds. This justifies preferring progressive availability and shorter occupation, without asserting a universal throughput win.

Thunderbird's full initial UID/flags inventory is the relevant research analogy (T07–T10). It does not prescribe this harness's metadata projection, descending order, parser or store. The experimental baseline deliberately batches metadata rather than reproducing Thunderbird's dense unbounded header dump. Nothing here benchmarks Thunderbird itself.

The progressive path uses actual observed UIDNEXT, closed numeric windows, exact returned identities and complete metadata before changing history coverage. Sender Date never defines membership. Moderate holes created by deletions are tested; logarithmic adaptive traversal of billion-sized gaps is not implemented or validated. It remains a separate liveness/performance obligation.

## Data lanes, notifications and real yielding

All 27 successful 50,000 + 10 runs obtained ten exact new identities while history continued and then verified every initial identity. Worst observed post-APPEND-completion wait was 465.05 ms, including the largest connection-profile tail. C1 uses one client-owned socket; C2 and C5-one use one data socket plus watcher. C5-two uses three client-owned sockets: history/fresh data, watcher and user data. The independent mutation actor raises observed total sessions by one. C5 does not imply five opened sessions or prove a provider cap.

The second data lane reduced the one simulated flag request's admission wait to about 0.1 ms. With one lane, worst FETCH-trigger admission waits were roughly 41–52 ms. BODY.PEEK admission from original intent also includes the preceding STORE; a second lane did not consistently improve it. No repeatable freshness or throughput advantage sufficient to justify concurrent authoritative synchronization writers was established. Retain one data lane as the next validation baseline. The optional watcher supplies early hints, but these frequent-boundary-polling trials do not establish a consistent tail improvement; measure it again at a realistic time-based poll cadence and impaired network.

A publication batch is not a yield. Here command iterators exhaust, the actual tagged responses are observed, transport scopes settle, and setImmediate returns an execution turn before reconsideration. IDLE/DONE completion is recorded before another command. One pending user request and a coalesced boolean hint avoid a promise queue per EXISTS. Finite trials cannot establish a long saturation plateau or multi-account fairness.

## Corrections required by the observed failures

1. **Fresh selection evidence:** STATUS on a selected Dovecot mailbox can report stale UIDNEXT until NOOP processes remote changes. The first smoke failure obtained only one arrival. Use a completed refresh/reselection before accepting fresh frontier observations; polling and notification hints remain independent of history completion.
2. **Unsolicited FETCH classification:** another connection's STORE or expunge can interleave flag-only FETCH inside a requested metadata/flags iterator. Such notifications may have a sequence number without UID. Phase 1B's strict helper rejected this legal traffic. The Dovecot adapter now retains bounded notification hints and never treats them as requested metadata or absence. Every requested metadata UID still needs one complete record; full metadata with unexpected/duplicate identity still fails. Reconciliation keeps complete known-set membership evidence and rechecks missing required flag rows.
3. **Timing oracle independence:** metadata can become visible before the actor's APPEND callback/command-completion event. Publication timestamps must be retained by actual UID independently of that callback. Eleven successful arrivals had negative signed completion-to-availability differences; the report preserves them and labels “already available at completion,” rather than inventing a delivery timestamp. Actual Dovecot APPENDUID/end_time events are saved; cross-clock latency remains uncertain.
4. **Active versus passive timing:** a ten-second socket inactivity timeout killed the independent actor after it finished appending while history still ran. Passive inactivity is now 60 seconds, while active destructive operation deadlines remain 10 seconds. A closed client is never evidence of successful cleanup/reuse; that failed run remains failed. A production owner must classify idle retirement and reconnect costs explicitly.
5. **Complete bounded membership:** full SEARCH over 50k exceeded the conservative 256 KiB line cap and was rejected. The destructive harness uses complete bounded inventories and known-set pages. No cap was increased after that failure. Successful numeric UID searches do not require a strict token-allocation patch.

These are required details at the experimental transport/evidence boundary. They do not require another synchronization engine or production library patch. The approved original design documents remain untouched; this review records findings for a later reviewed revision.

## Remote changes and recovery

The successful D run deletes 15,000 identities in bounded batches while independently discovering ten old-Date arrivals. Two bounded reconciliation passes converge to exactly 35,009 current server UIDs in 25.21 seconds; worst arrival wait is 326.94 ms. The total includes an earlier SEARCH/FETCH victim, equal-count churn and eleven added change-fixture messages. CONDSTORE returns one changed flag row versus 128 full-fallback rows for the same requested page (2.06 versus 12.62 ms). This single page demonstrates traffic reduction, not a mailbox-wide performance or stale-MODSEQ guarantee. Complete membership checks remain necessary with both methods.

Missing metadata after a genuine expunge rejects the operation, destroys the unusable client and advances no boundary. A fresh selected client confirms same-epoch absence before resolving the gap. A complete read replay preserves placement uniqueness. Partial FETCH cancellation publishes zero rows and then replays 128 records on a fresh client. Connection rejection occurs after eight additional sessions with two already active, matching the disposable server limit of ten; it proves this configured Dovecot behavior only.

UIDVALIDITY testing uses supported creation, deletion and recreation of a separate mailbox. The epoch changes from 1791800365 to 1791800366 and the old epoch is rejected. INBOX indexes and UID files are never fabricated. Epoch changes during an already-started production database commit remain untested.

The two-process JSON checkpoint proves orderly frontier restoration and continued descending work. It has no fsync or transaction contract and does not prove durable crash recovery. PostgreSQL, pg-boss, lease takeover, unknown commit, notification deduplication and production lifecycle fences have not been validated. D ran against the previously verified local model during reconciliation, not simultaneous rebuilding of every historical record. D/E have one destructive end-to-end run; they are not the three-profile repeated race matrix.

## Resource contract and remaining obligations

The user-approved direction supersedes strict parser K allocation: K=128 sizes admitted work, with conservative parser limits and aggregate decoded-input budgets. A real Dovecot response exceeds a deliberately 1,024-byte aggregate budget by 1,180 bytes before rejection; zero bytes from that chunk are admitted, the socket closes and no metadata is published. The 46-case scripted regression preserves larger token/byte amplification counterexamples, depth failures, incomplete data, wrong content origin and delayed watchdog behavior.

The real-server adapter still uses pinned private ImapFlow hooks and logger diagnostics. Its memory samples include stored metadata/oracle/trace arrays. Neither a two-MiB wire budget nor finite measured RSS proves a strict whole-process allocation ceiling. Compression, IMAP4rev2, hostile ESEARCH expansion across all helper variants, oversized MIME semantics and parser CPU isolation remain unproven. A responsive event-loop watchdog cannot promise an unconditional wall-clock bound through a synchronous 1.8-second inventory stall or process suspension.

SEARCH and FETCH each have a 10-second operation scope here. The architecture's single deadline spanning refresh, SEARCH, FETCH and a fenced database commit still needs integrated validation. No production implementation may adopt the internal helpers as approved APIs. Next validation should add isolated durable atomic progress/fencing, a controlled RTT/bandwidth profile, time-based polling, deterministic remote barriers where available, per-account fairness/resource saturation, and provider/content compatibility. The current evidence supports that work; it does not satisfy the production gate.
