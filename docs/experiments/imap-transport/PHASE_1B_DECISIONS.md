# Phase 1B transport decisions

Date: 2026-10-12 (Europe/Warsaw). Based on the installed ImapFlow 2.0.6 ESM source and actual loopback TLS trials in [PHASE_1B_RESULTS.md](PHASE_1B_RESULTS.md). Base commit `3b0745726fa107e7d26567267937440a5de31b25`; branch `experiment/imap-transport-hardening`. Historical reports and architecture are preserved.

**BLOCKED — TRANSPORT ADAPTATION REQUIRED.** Keep ImapFlow 2.0.6 as the dependency candidate. Its existing parser limits and connection teardown are useful. The experiment resolves several acceptance boundaries without a dependency fork, but cannot satisfy strict preallocation of at most K parser identities. Do not start Docker/Dovecot Phase 2 until that bound has a narrow reviewed adaptation, or the user explicitly approves a different bounded-allocation contract. This task does not make that tradeoff on the user's behalf.

## H1 — SEARCH accumulation and parser allocation

1. **Original failure:** results accumulate across SEARCH replies, return only at command completion, accept out-of-range IDs and are bounded only by a very large library expansion ceiling. A numerical interval bounds compliant identities, not bytes, allocations, CPU or server processing time.
2. **Candidates evaluated:** existing line/literal/response configuration; array postcheck; native decrypted socket observer; parsed-response handler observation. Public postchecks are too late. Per-response caps reset. Socket observation bounds total admitted input, but a chunk is already allocated. Parsed observation prevents further library collection but token allocation already happened. ESEARCH's compact range can expand far beyond its wire size; it is rejected before expansion in this experiment.
3. **Simplest working approach:** configure all three parser caps, count aggregate incoming bytes before the socket's existing pipe listener, inspect parsed SEARCH IDs before the original handler, close/invalidate on overflow, validate numerical interval/UID uniqueness, then require completed array evidence. This is a reliable bounded-input/collection experiment for the uncompressed TLS rev1 profile. It is not an at-most-K parser-token contract: a retained baseline scenario demonstrates 16,384 already-created tokens despite collection stopping at 128.
4. **Production change required:** if strict K remains required, add an operation-scoped check before SEARCH token/node creation in `handler/token-parser.js` (with context supplied from `imap-flow.js`), maintaining count across replies, before constructing the 129th identity. Legacy SEARCH, duplicates/invalid atoms and compact ESEARCH expansion in `commands/search.js` must share the budget and fail explicitly; silently truncate is insufficient. For exact admitted parser-byte budgets, add a scope hook at `handler/imap-stream.js` before chunk processing/literal allocation, after decompression. Document bounded current-chunk/TLS/allocator headroom separately. A parsed-result event alone cannot solve token preallocation.
5. **Cost/complexity:** no new runtime dependency or IMAP client. One pinned internal observer is sufficient for this experiment. Strict K needs a small cross-parser context/budget change and source-faithful regression tests; it should be isolated from the existing STORE patch. No measured development-effort estimate is claimed.
6. **Remaining risks:** complete line/token copies and formatter allocations; unread Node/TLS/kernel buffers; byte-derived token overhead; compact ESEARCH/range expansion; buffered unsolicited input before the operation; source upgrades; parser CPU blocking watchdog. Physical memory is not equal to logical IMAP bytes.
7. **Architecture:** one owner and command-sized work remain appropriate. The at-most-K buffered identity acceptance statement needs either the described adaptation or explicit revision distinguishing collection cardinality, token allocation and transport overhead. No document was amended silently.

## H2 — Complete metadata evidence

1. **Original failure:** tagged OK with missing UIDs; excessive parser depth drops a row; many sub-cap headers exceed a command aggregate. None of these establishes absence or complete coverage.
2. **Candidates evaluated:** `fetchAll` plus count checks; iterator with exact requested identities; public error listener and scoped warn/error logger; aggregate socket budget plus parser caps. Count alone cannot detect a duplicate replacing a missing identity. Application byte checks alone follow allocation.
3. **Simplest working approach:** experiment-only `metadata()` accepts distinct UIDs ≤128 and an explicit expected mailbox/UIDVALIDITY. Exhaust the iterator, verify each UID and required fields, then validate selected epoch again and call external publication validation. Accept only the exact set; otherwise return unresolved/incomplete. Reject scoped parser failures immediately, preserve root diagnostic and destroy the client. Missing identity message explicitly requires recheck and makes no absence/frontier claim.
4. **Production change required:** implement complete application metadata validation and same-epoch missing-UID membership recheck; wire the external check to real account/mailbox lifecycle and a fenced transaction. Scope parser failure diagnostics to stable command/operation IDs instead of logger conventions. Integrate aggregate input accounting with the approved parser bound. Do not directly import the experimental adapter as a production service.
5. **Cost/complexity:** one bounded map/set plus finally-safe iterator/executor behavior; no pending UID tables, receipts, database migration or additional engine. Experimental failure closes a selected connection conservatively, potentially costing reconnect/authentication.
6. **Remaining risks:** missing UID can be genuine expunge, deliberate omission or parser loss; wrapper cannot choose which. Persistent omissions can stall progress and must be visible. Field presence is not complete MIME/envelope semantic validation. Selected epoch and callback are not proof of durable owner/epoch fencing or a remote snapshot.
7. **Architecture:** existing exact identity comparison, no false deletion and unresolved frontier policies are reinforced. No new durable state or changed ingestion algorithm is justified. Real transaction/publication work remains a later task.

## H3 — Partial content origin and finality

1. **Original failure:** public raw fetch accepts wrong origin and oversized literal. Correct returned length alone cannot identify the returned slice's actual offset.
2. **Candidates evaluated:** public `bodyParts` map, per-literal cap, installed token metadata, internal handler interception, continuous versus independent slice decoding. `tools.js` builds a section-keyed Buffer map and loses `partial`; the token parser has preserved the actual partial origin. A literal cap restricts bytes but cannot validate that origin.
3. **Simplest working approach:** intercept the real parsed FETCH before formatting; require the requested UID, one BODY section, matching numeric origin, exact expected length and one observed result. Reject BINARY/extra parts/duplicates/mismatch. Fully exhaust the command before accepting each slice. Keep one Base64 or quoted-printable decoder across all successful slices. On an interrupted part, discard every accumulated encoded/decoded buffer and the decoder; reconnect and restart at zero. Independent source-byte equality is the completion oracle in the experiment.
4. **Production change required:** expose actual `{section, origin, length, response encoding}` through a stable parsed-response hook or additive formatter metadata in `tools.js`/types. Preserve multiple responses rather than silently map-overwriting duplicates. Finalization must validate a reliable encoded part length or an explicitly justified EOF protocol plus current durable epoch/owner. Retain incomplete cache status until validated end. Add provider/MIME/charset/decoder-error validation in the later content task.
5. **Cost/complexity:** a few validations at the response boundary plus one live decoder. Restart consumes repeated bytes but avoids durable slice cursor/decoder-state persistence. This phase provides no evidence that serializing decoder state is necessary.
6. **Remaining risks:** our expected encoded length is a fixture oracle; future metadata length may be stale or invalid. Synthetic exact equality does not prove arbitrary MIME, cache atomicity or charset correctness. A server can return wrong bytes while lying consistently about origin; protocol metadata is a trust boundary, not content authenticity. The public Buffer alone remains insufficient.
7. **Architecture:** separate slice operations and continuous decoder fit the design. Explicitly approve discard/restart and origin proof at a reviewed transport boundary. No durable content progress mechanism is added, and the protected architecture remains unchanged.

## H4 — Absolute deadlines, cancellation and work settlement

1. **Original failure:** inactivity is defeated by trickle; Promise.race can leave active requests; resolved NOOP can mask hung DONE; close cannot revoke already-resolved data/callbacks; timers run late under CPU blocking.
2. **Candidates evaluated:** socket timeout, Promise.race, single monotonic operation clock, destructive close, retained native socket, token guards, fresh-client recovery. Socket timeout remains separately useful for inactivity. Promise-only expiry is rejected. No worker thread/external watchdog was introduced.
3. **Simplest working approach:** one deadline from `performance.now()`, remaining-time callback, timer plus boundary checks, token invalidation before close. Await actual work settlement and native socket close; require peer-close evidence in tests before recovery. Every authorizing boundary checks the old guard. A fresh client searches UID 9 after faulted work. Preparation and cleanup consume the same deadline; there is no per-command reset.
4. **Production change required:** carry the deadline/token through connection setup, DONE/selection, parsing, DB admission, statements and cleanup. Provide explicit cancellation and uncertainty settlement for application/DB work, plus durable owner/epoch fences at publication. Reconnect only after local affected transport retirement, retaining remote-session expiry limitations. For mutations, record uncertain outcome and reconcile instead of blind replay.
5. **Cost/complexity:** one timer/token per operation and destruction/reconnect when unusable. Existing library teardown suffices for tested network operations. No extra data lane or general transport framework is necessary.
6. **Remaining risks:** a 140 ms event-loop block prevents a 40 ms watchdog firing on time. Native close cannot settle arbitrary application promises; the cleanup trial closes near its deadline but returns unresolved only when its delayed work settles. Native and peer close are local evidence, not a provider session-retention guarantee. The mutation trial proves an actually received STORE with no response is ambiguous, not whether it executed remotely.
7. **Architecture:** one absolute deadline and rejection of late publication are confirmed under responsive execution. An unconditional wall-clock limit would need a separately reviewed isolation/watchdog design only if required by the product; this task does not add one to make a stronger claim.

## H5 — Error evidence and correlation

1. **Original failure:** APIs may return false or resolve with incomplete data; parser failures live in logs, underlying errors are replaced by NoConnection, and NOOP can resolve without execution.
2. **Candidates evaluated:** thrown/returned results only; error events only; warn/error logger only; combined single-owner scope with active request tag/command. Logger-only collection failed the ETIMEOUT assertion; adding the public event preserved the cause. Exact-set evidence is necessary even when no diagnostic fires.
3. **Simplest working approach:** minimal categories `authentication`, `connection`, `socket-timeout`, `deadline`, `cancelled`, `parser-limit`, `malformed`, `budget`, `incomplete`, `epoch`, `protocol`, `unresolved`; preserve underlying cause in operation diagnostics. Separate `remoteOutcome=ambiguous` for failed mutation scopes. Parser errors with an active sent request are correlated to its tag; missing correlation rejects as unresolved, never successful progress. Warnings without structured error are likewise conservative unresolved failures.
4. **Production change required:** provide a stable command-scoped diagnostic hook in `imap-flow.js` at token parse/response failure, before the request tag is cleared; include connection and operation ID. Public error events must be collected as well as thrown errors. Future scheduler/retry policy must treat incomplete/epoch/ambiguous outcomes independently and avoid replaying a mutation just because reconnect succeeds.
5. **Cost/complexity:** one collector per owned client/scope; no generalized taxonomy framework. Stable diagnostic exposure is a narrow source/API change; conservative logger-based fallback incurs false-negative compatibility/reconnect costs.
6. **Remaining risks:** tagged NO and disconnect logs can follow request clearance, so their active command cannot be reconstructed reliably from that log alone. The raw diagnostic still retains protocol/connection cause; result is unresolved. Concurrent commands/IDLE callbacks, source changes and swallowed diagnostics invalidate stronger correlation claims. A log entry's absence does not prove the command was valid; result validators still run.
7. **Architecture:** preserve explicit retry/error/unresolved outcomes and no progress from incomplete evidence. Error taxonomy can be added as a small transport contract; there is no need for another scheduler or synchronization engine. Any public diagnostic contract or patch needs separate production review.

## Dependency patch surface and approval boundary

No new dependency patch was applied. The baseline reproductions remain independent of instrumentation: original Phase 1 and `raw-wrong-origin` use the installed parser/client directly. `search-parsed-overshoot` proves why a post-token hook cannot supply strict K even with the experimental collection guard.

If strict K is retained, the minimum next adaptation is operation context with a token-creation/compact-range budget and explicit parser failure notification. Origin exposure can reuse that parsed-response context; it does not require a broad library fork. Input budgets must be applied after decompression and must state current-chunk/native overhead. Implementing a proposed patch in production or changing the architecture's strict bound is not authorized by Phase 1B.

Explicit user decisions required before further work: retain strict parser K and authorize a narrow transport adaptation task, or approve a documented byte-derived allocation/headroom contract and revise the architecture gate. Production patch adoption, provider compatibility limits, unreliable part length policy and an unconditional deadline requirement require their own review. This report does not request permission to finish this phase: its authorized experiments/reports are complete and committed. No Phase 2 run, push, PR or merge is performed.
