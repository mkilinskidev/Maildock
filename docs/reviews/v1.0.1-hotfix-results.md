# Maildock v1.0.1 IMAP hotfix results

Date: 2026-10-09. Branch: `fix/v1.0.1-imap-performance`. Implementation baseline: freshly fetched `origin/test`, `db303d04f311f397d38fa10ad62c84b57ca144d4`. Working tree was clean before branch creation. Investigation reports were read and independently checked against current source and installed ImapFlow 2.0.6 / pg-boss 12.33.7. Production was not accessed, changed, migrated, restarted or deployed. No push, main merge, release tag or release was created.

## 1. Findings addressed

The confirmed source-level excess work was sequential presence SEARCH in metadata-sized batches of 150. The hotfix reduces those requests, preserves deletion evidence and adds the stage timing needed to distinguish provider execution from setup and persistence. It also addresses missing explicit timeout classifications, loss of the original asynchronous socket exception, UI failure presentation while automatic retry remains live, and interrupted pending writes without durable enqueue. Gmail throttling, OAuth latency and particular remote commands remain unconfirmed causes of observed production latency.

## 2. Reconciliation algorithm and alternatives

Use independent presence bounds: 1,000 requested UIDs and 8,000 UID-set characters. Requests explicitly enumerate only snapshot UIDs. SEARCH ALL was rejected because unindexed history can be much larger than the snapshot, full responses have weaker practical memory bounds, and the installed parser can discard/truncate malformed entries without exposing a completeness indicator. Gmail uses the same generic path as other providers.

Validate response type, integer/32-bit bounds, requested membership and duplicates. Accumulate missing UIDs without deleting. Independently issue bounded UID-only FETCH for missing candidates and drain each generator; a returned UID contradicts SEARCH and fails reconciliation, and false completion is rejected. This catches a successful but partial SEARCH response without silently falling back. STATUS and client-health checks precede deletion. Deletion persistence remains bounded to existing metadata batch size. Only then can completion persist MODSEQ. Returning false from a guarded/instrumented generator is preserved.

The snapshot belongs to the selected UIDVALIDITY. Existing epoch reset and recent-window bootstrap/recovery remain unchanged. Only snapshot placements can be removed; reconciliation never imports historical UIDs. Arrivals after new-UID detection are left for the next delta, while expunges witnessed during reconciliation are removed. An expunge after a presence result converges on the next pass. New-message UID frontier persistence still occurs per committed batch, so a later failure can retain useful committed new metadata without declaring complete reconciliation. SELECT MODSEQ, rather than a later STATUS value, remains the conservative checkpoint.

Both independent commands must obey IMAP completion semantics. A broken server falsely omitting the same valid UID from both successfully completed SEARCH and FETCH cannot be proved correct by this client. Rejected, malformed, contradictory, interrupted and timed-out results fail closed.

## 3. Instrumentation

`mail.performance` emits one aggregate monotonic summary per operation/attempt. Nested provider and Google work share the service trace. Fields are explicitly selected: operation, random correlation ID, attempt, success, safe category/code, failing stage, durations/call counts, local/returned UID counts and CONDSTORE use. No addresses, folder paths, UID values, subjects, bodies, MIME payloads, credentials, raw exceptions, stacks or protocol traffic are added to telemetry. Logging exceptions are swallowed at the summary boundary and do not change outcomes. Normal as well as slow/failed attempts are retained; there is no per-message or per-command event stream.

Delta stages: credentials, combined IMAP connect/authentication, selection, new UID work, flag processing, presence/absence confirmation, STATUS, sink persistence, teardown and overall service execution. Content stages: queue metadata, credentials, connect/authentication, selection, local MIME selection, selected FETCH including stream consumption, sanitization, ready persistence, teardown and overall attempt. Queue eligibility delay uses PostgreSQL started/start-after timestamps; original queue age includes previous attempts/backoff and must not be described as ordinary dispatch wait.

Google credential acquisition measures pool/transaction/row-lock acquisition through completion of SELECT FOR UPDATE separately from token HTTP/response validation and total acquisition. This does not isolate pure server lock wait from pool checkout/query duration. Locking, refresh rotation and revocation semantics are unchanged. Connect/authentication is a combined ImapFlow API span. Generator timings can include downstream persistence while processing yielded rows; stage sums are not necessarily exclusive. Correlation IDs identify aggregate operation summaries, not browser selection events.

## 4. Timeout diagnostics

Code-first recognition covers CONNECT_TIMEOUT, GREETING_TIMEOUT, UPGRADE_TIMEOUT and ETIMEDOUT as connection timeouts; ImapFlow ETIMEOUT is socket inactivity. Authentication, TLS certificate failure, provider disconnection and cancellation retain distinct categories. Safe normalized code/stage are retained before wrapping. Guarded promises, generators and content stream errors preserve the first asynchronous socket failure instead of secondary connection-close errors. Positively acknowledged mutations retain their existing behavior. Browser and durable job errors remain controlled text. Socket timeout values are unchanged.

## 5. Content retry behavior and recovery

The persisted attempt state remains compatible with the existing schema. Web detail presentation consults durable jobs: active becomes fetching, created becomes pending, and delayed retry becomes pending plus `retrying=true`. Reader polling continues and shows an automatic retry notice, then observes ready content after success. Terminal jobs produce failed presentation. Already-ready current-policy content bypasses job lookup/fetch.

All content producers serialize under a transaction advisory lock and coalesce across created, retry and active states. Manual retry cannot reset delayed retries or create active successors. Queue metadata is resolved before reserving transaction connections, avoiding lazy-cache pool exhaustion under concurrent producers. Stately policy, retry limit four (five total attempts), jitter/backoff, 900-second delay cap and 900-second expiration are unchanged.

Pending generations use the PostgreSQL clock; terminal-job timestamps distinguish retained older work from an interrupted new enqueue. Open-reader polling repairs missing work. A readiness-controlled worker sweep pages up to 100 pending/fetching placements every 60 seconds, with a cursor and no overlapping runs. A stable backlog of N placements is revisited within approximately `60 * (ceil(N/100) + 1)` seconds plus query/execution time. Active or delayed jobs are never declared abandoned based on elapsed application time. pg-boss expiration/retry handles worker loss; terminal jobs are not automatically resubmitted. The sweep settles terminal pending/fetching rows to failed, and stops/awaits in-flight maintenance before worker shutdown.

Failure and state-transition predicates protect a successful cache from stale outcomes. A late expired attempt's failure cannot replace a later ready cache, and stale success cannot replace an already valid ready cache. SQL IS DISTINCT FROM keeps ready caches with null/old HTML policy versions refreshable. Remote-image policy, HTML isolation and interactive-only body scheduling are preserved; no body prefetch was added.

## 6. Fairness evaluation

No hard account gate is shipped. A real PostgreSQL regression demonstrates that two simultaneous transactions can claim separate mailbox jobs for the same account with installed `groupConcurrency: 1`: each sees no committed active group before the other commits. This is an execution-admission race, not a reliable distributed exclusion primitive. A worker-side waiting lock would still occupy capacity; retry/requeue admission can exhaust required work. Existing ungrouped durable jobs also need a transition design.

A separate account-aware durable claim/lease design is recommended, with atomic exclusion before credentials, crash recovery, bounded deferral, existing-job transition and multi-worker tests. Reduced delta occupancy is useful but is not a guarantee against cross-account starvation. Global concurrency remains unchanged; no extra Gmail sessions are introduced.

Deterministic injected-provider fixture, unchanged mailbox, 41,246 known sequential UIDs, metadata size 150, existing CONDSTORE checkpoint:

| API calls during selected-mailbox reconciliation   | Before | After |
| -------------------------------------------------- | -----: | ----: |
| Known-UID presence SEARCH                          |    275 |    42 |
| All SEARCH (including new UID detection)           |    276 |    43 |
| Changed flags FETCH                                |      1 |     1 |
| STATUS                                             |      1 |     1 |
| Total above (excluding connection/select/teardown) |    278 |    45 |

Presence commands fall by approximately 84.7%. No missing UID means no extra absence-confirmation FETCH. At maximum 10-digit UID width, the character cap requires 57 presence requests, still substantially below 275. Without CONDSTORE, known flag FETCH remains metadata-batched and can still dominate. This is a local command-count benchmark, not a Gmail latency benchmark or production improvement claim.

## 9. Limitations, deployment and rollback

The branch is intended for code review. Standalone browser security verification passed on recheck. Real Gmail/provider timing, networking and post-deployment performance remain unverified. Hard account fairness is deferred. QRESYNC is still not used for VANISHED reconciliation. Existing active expiration can permit an old in-process attempt to outlive its durable job; cache guards address stale outcomes but do not implement provider cancellation/preemption.

No schema or persistent queue-option migration is required. Deploy only through a separately authorized release task, on the normal Linux build path, after review and verification. New pending generation timestamps and retry presentation remain schema compatible. Prefer reverting the complete hotfix set for rollback; selective algorithm/telemetry rollback is possible, but reverting retry presentation alone restores the old UI/recovery defects. Preserve pending queue jobs, caches and checkpoints. Do not clear queues, reset MODSEQ/UID frontiers or widen timeouts as a rollback shortcut. Source package version remains the baseline value; release/version/tag preparation is separate.

Post-deployment metrics: per-stage delta/content p50/p95/p99, presence command count/local UID count, safe timeout code and failing-stage rates, OAuth acquisition versus lock/HTTP spans, content eligibility delay versus attempt duration, queue age by account, both delta slots' account occupancy, oldest other-account job age, retries/exhaustion, interrupted-enqueue repair, deletion counts, epoch resets, frontier progress, and HTML/remote-resource privacy regressions. Reconcile representative controlled mailbox snapshots and monitor generic providers as well as Gmail. Do not conclude production is resolved before separately deployed telemetry confirms correctness and improvement.
