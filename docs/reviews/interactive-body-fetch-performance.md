# Interactive message body fetch performance investigation

## 1. Executive summary

Investigation date: 2026-10-09. Reviewed latest fetched `origin/main`, commit `ba074880768645473af070ecc846e420ced990d5`, also the local `v1.0.0` tag target. Branch: `investigation/interactive-body-fetch-performance`. This report is the only change; application code, tests, migrations and configuration remain untouched. No production access, runtime traces or performance reproduction were available. Source establishes contention mechanisms, not the cause or distribution of the reported approximately 20-second delay. Verify the deployed image SHA, dependency versions and effective settings before applying conclusions to production. `package.json:3` still says `0.1.0`; the Git tag and image identity are more useful release identifiers.

Additional production evidence supplied on 2026-10-09: the reader displayed **“The connection timed out.”** with **“Retry download”** for the Gmail account. This establishes a user-visible body retrieval failure, not just slow retrieval. Section 11 traces its origin, narrows the possible timeout stages and recommends reliability fixes. The screenshot does not reveal the original exception or failing IMAP command; these were not retained by the current error pipeline.

The suspected shared queue/shared IMAP connection explanation does **not** match this implementation:

- Interactive bodies already use `message-content-fetch-v1`, independently of recent, delta and historical sync queues. Content has one local execution slot per worker process, shared by all accounts. Background jobs do not occupy that slot, but other body requests do.
- Every provider operation creates its own IMAP client. Content does not acquire the PostgreSQL mailbox sync advisory lock and does not wait for a shared IMAP pool or mailbox-selection lock.
- **There is account-level serialization before IMAP for Google OAuth.** Every credential acquisition refreshes an access token while holding `SELECT ... FOR UPDATE` on the account row. Sync, discovery, body fetch and IDLE reconnection all use this resolver. Concurrent acquisitions wait for preceding token requests; each token HTTP request has a 15-second timeout. This is a concrete contention mechanism, conditional on the production account using Google OAuth. Its contribution to the incident is unmeasured.
- Content dispatch uses pg-boss's default two-second polling, with no queue notification opt-in. The frontend adds adaptive polling delays of 400, 800, 1600 and then 2500 ms at default settings. Provider cleanup is awaited before body sanitization/persistence. These are separate latency sources.
- Gmail message identity is recognized through ImapFlow's `X-GM-MSGID` mapping, but metadata persistence creates a new local message for each new folder/UID placement. All selectable labels are independently synchronized; there is no cross-folder body cache sharing.

Do not hotfix this by increasing priority alone or creating another sync-versus-content queue. Preserve the existing isolated content queue. First measure queue wait, credential row-lock/token time, IMAP stages, database time and browser observation separately. The smallest low-risk dispatch improvement is an explicit 0.5-second content worker polling interval, subject to validation of database overhead. This cannot promise responsiveness under resource contention. If OAuth/background contention is confirmed, the smallest robust next step is bounded account-aware background admission **before credential acquisition**, leaving interactive resource headroom and preserving OAuth locking/rotation behavior. Consider a second content slot only when body head-of-line blocking is measured and deduplication/retry races are covered. No implementation is authorized by this report.

### Priority, ordering and retry semantics

Installed pg-boss defaults `batchSize` and local concurrency to 1 and priority ordering to true (`node_modules/pg-boss/dist/manager.js:843`). Default polling is **2000 ms**, minimum configurable interval **500 ms** (`dist/attorney.js:579`). Queues default `notify` to false (`dist/plans.js:684`); the content queue does not opt in. Worker awaits the handler before fetching again and subtracts iteration duration from its polling interval (`dist/worker.js:53`). A long body job holds its own local slot throughout credentials, network, teardown and persistence. It does not hold another queue's slot.

`fetchNextJob` filters the named queue, eligible state/start time and relevant singleton constraints; candidates sort by `priority DESC, created_on`, then are claimed using row locking (`dist/plans.js:1617`, `:1752`). Thus higher priority can overtake **eligible pending jobs in the same queue**. It cannot preempt active work, override future retry `start_after`, bypass key ownership or rank work globally across these queues. Recent/delta priority 10 does not outrank content priority 0 across queue names, nor does historical -10 itself guarantee host-resource fairness. Equal creation timestamps do not establish a strict selection-order guarantee.

Content retries: limit 4, delay 30 seconds, exponential backoff, delay cap 900 seconds, active-job expiration 900 seconds (`src/modules/mail/infrastructure/content-jobs.ts:20`). These are recovery settings, not a 20-second end-to-end deadline. Retry timing is jittered in pg-boss, not necessarily exactly 30 seconds. Ready persistence precedes job completion, so a retry after lost completion can short-circuit ready content. UI stops automatic polling on `failed`, even if pg-boss will retry later; it requires a new selection/retry to reliably observe subsequent success. Manual retry can create a successor with the same key in a different state. Inspect actual queue rows rather than inferring job success from a 202 or content status alone.

## 3. Evidence-backed findings

### F1. One global local body slot creates head-of-line blocking

Confirmed capacity constraint, incident contribution unknown. `content-jobs.ts:69` fixes concurrency at 1 across accounts, regardless of `WORKER_CONCURRENCY`. Already-running downloads and stale selections can delay current selections. Raising priority for every interactive job equally changes nothing about this backlog. Multiple worker processes multiply capacity; it is not a deployment-wide limit.

### F2. OAuth creates a genuine account-level wait before IMAP

Google `accessToken` starts a transaction, takes an account row lock, and **always** sends a refresh-token request while holding it (`src/modules/accounts/infrastructure/google-oauth.ts:372`, `:385`, `:391`). The HTTP timeout is 15 seconds (`:131`). There is no access-token cache to allow other acquisitions to skip refresh. A token request waiting behind N acquisitions can spend their cumulative lock-hold time before its own request; the token HTTP timeout does not bound that prior lock wait. Lock-waiting transactions also occupy application DB connections and can delay work on other accounts through pool exhaustion.

Microsoft similarly takes an account row lock but uses an MSAL cache (`src/modules/accounts/infrastructure/microsoft-oauth.ts:308`, `:324`, `:359`). Password accounts do not use this OAuth path. There is no evidence of a whole-account IMAP mutex. The existing OAuth serialization protects rotation/reconnection/revocation correctness; removing the lock is not a safe performance fix. No token caching/authentication changes are recommended for a v1.0.1 hotfix without a separate security and recovery review.

### F3. Independent IMAP clients already isolate protocol operations

Confirmed from provider `createImap` (`src/modules/accounts/infrastructure/imap-smtp-mail-provider.ts:672`) and per-operation creation at `:873` (recent), `:947` (backfill), `:1056` (delta), `:1373` (body). No application account connection maximum/pool/admission controller is implemented. A single provider instance does not imply a shared client. Folder selection serializes commands on each client, but content and sync select on different clients. Normal content fetch does not invoke `getMailboxLock`.

The PostgreSQL sync advisory lock is scoped to mailbox ID. It first reserves a pool connection, then uses **try-lock**, throwing immediately if busy (`src/modules/mail/infrastructure/mailbox-lock.ts:5`). Pool reservation can wait; a busy advisory lock itself does not block there. Content worker registration does not use this lock (`src/composition/worker-process.ts:105`, `:110`). Metadata `persistBatch` locks the mailbox row inside its transaction (`src/modules/mail/application/message-service.ts:377`); ordinary detail SELECTs do not directly wait for that row lock under MVCC. Concurrent writes to matching message/attachment rows and shared DB load can still contend. Do not attribute GET latency to a sync row lock without evidence of its actual blocking query.

Separate body connections are already used safely with read-only selection and UIDVALIDITY verification. Adding more connections needs aggregate account/provider limits, including IDLE, commands/attachments, other Maildock processes and other email clients. IMAP timeouts are 10 seconds for connection/greeting and 15 seconds for socket inactivity (`src/modules/accounts/infrastructure/imap-smtp-mail-provider.ts:53`, `:202`), not a total operation deadline. Cleanup can delay availability after bytes have downloaded. No application cancellation/preemption contract exists. Safest yielding boundaries are fully drained FETCH plus committed/checkpointed metadata; closing a connection mid-command or advancing a frontier before persistence risks recovery errors. Preserve mutation acknowledgement handling in `imap-client-lifecycle.ts:8`.

### F4. Shared compute/database capacity can defeat queue isolation

Confirmed sharing, saturation unmeasured. Recent and delta have independent concurrency budgets and backfill another slot; one Gmail account can have several folder operations in flight. Pool sessions held for sync locks, OAuth transactions and batch transactions can reduce the 10-connection application pool's headroom. Synchronous normalization/sanitization/search processing uses the worker's event loop. pg-boss fetch/maintenance SQL shares PostgreSQL CPU/I/O with synchronization despite separate client pools. Increasing every concurrency limit can worsen these waits.

### F5. Persistence and queue insertion are not atomic

`request` checks state, upserts pending, then sends outside a shared transaction (`message-content-service.ts:124`). Concurrent callers can both pass the read; queue key policy reduces duplicate same-placement jobs but is not an atomic application-state claim. `stately` has uniqueness per queue/**state**/key (`node_modules/pg-boss/dist/plans.js:811`), allowing an active job and created successor; it is not exclusive across every live state. Pending/fetching normally suppress repeat requests; rejected duplicate send returns false, still a 202.

A process crash after pending persistence but before enqueue can orphan pending state. No body-state repair poller is registered alongside the attachment/outgoing/sync pollers (`src/composition/worker-process.ts:88`). Worker loss after a durable job starts should be recoverable via pg-boss expiration/retry, but this can be much longer than interactive expectations. Retry exhaustion, manual retry versus existing retry, a successor finishing out of order, and UIDVALIDITY/move races require explicit testing before changing concurrency or adding queues. These are reliability findings, not a confirmed explanation for a normal successful 20-second fetch.

### F6. Browser observation is measurable additional latency

`contentPollDelay` doubles every five seconds and caps at 2500 ms (`src/shared/application/content-polling.ts:1`). At default settings, delays are 400 ms in seconds 0–5, 800 in 5–10, 1600 in 10–15 and 2500 thereafter. Timer scheduling follows completion of a GET/POST, so response time adds to the interval. Hidden-tab timer throttling can increase it. Polling can amplify DB load because `detail` repeatedly attempts attachment inserts (`src/modules/mail/application/attachment-metadata.ts:15`) and queries attachment lists. This component alone does not explain a normal 20-second delay, but it must be separated from backend readiness.

### Proposed lightweight instrumentation (not implemented)

Use an opaque selection/request correlation ID; carry it through scheduler/job and return or associate a durable job ID. A repeated request should link to the existing body operation rather than inventing a separate execution trace. Allowlist account/mailbox/message IDs, queue, attempt, cache outcome, status, duration, byte count and part count. Do not emit addresses, subject, folder path, MIME content, URLs, credentials/tokens, raw provider responses or exception stacks. IDs still require normal log access controls/retention.

Record these structured events:

1. Browser `message_selected`; backend `request_received`, auth complete, `body_cache_lookup` hit/miss/stale/pending.
2. `body_pending_persisted`, `body_job_enqueued` with send result/job ID; `body_job_started` and attempt.
3. Credential DB checkout complete, account row lock acquired, token request start/end (safe category only), credentials ready.
4. IMAP admission wait/acquired if admission is added; today label this stage `imap_connect_started/completed`, since there is no pool to acquire. Then folder selected, each part FETCH start/end and decoded byte count.
5. Mailbox close/logout complete, sanitization/search processing complete, body persistence complete, handler complete.
6. Browser ready response observed, body text visible, HTML document visible; CID/remote-resource completion tracked separately.

Use `performance.now()` or `process.hrtime.bigint()` for local stage durations. Use browser monotonic timing for selection-to-display. Do not subtract monotonic clocks from different processes. Queue timestamps from the same PostgreSQL clock can measure queue residence; carry wall-clock timestamps only for trace alignment and document skew. Include retry ready time separately from original enqueue time; `started_on` can describe the latest attempt rather than the first. Keep sampling enabled for normal successful requests and retain slow/failure spans without logging content.

For an initial read-only runtime investigation, sample these projections using the deployed pg-boss schema/table (default is `pgboss.job`; verify actual partitioning first):

```sql
SELECT id, name, state, priority, retry_count,
       created_on, start_after, started_on, completed_on
FROM pgboss.job
WHERE name = 'message-content-fetch-v1'
ORDER BY created_on DESC
LIMIT 100;

SELECT pid, application_name, state, wait_event_type, wait_event,
       clock_timestamp() - xact_start AS transaction_age,
       pg_blocking_pids(pid) AS blocking_pids
FROM pg_stat_activity
WHERE datname = current_database()
  AND (application_name LIKE 'maildock%' OR cardinality(pg_blocking_pids(pid)) > 0);
```

Avoid selecting job `data`/`output`, raw SQL query text or connection credentials. Empty blockers do not disprove client-side pool waiting or network delay. Current rows/updated timestamps alone cannot reconstruct all prior attempts. Baseline idle and sync-loaded runs with identical local cache misses, then compare stage p50/p95/p99, failures, retries, pool waits and sync progress. Do not clear production caches or create load on the production mailbox for this investigation.

## 5. Gmail-specific observations

Google documents that Gmail IMAP provides `X-GM-MSGID` and label attributes ([Gmail IMAP extensions](https://developers.google.com/workspace/gmail/imap/imap-extensions), checked 2026-10-09). Installed ImapFlow always requests EMAILID when OBJECTID is available, otherwise X-GM-MSGID when X-GM-EXT-1 is advertised (`node_modules/imapflow/dist/esm/commands/fetch.js:76`); it maps both into `emailId` (`dist/esm/tools.js:675`). Consequently the recent query need not explicitly say `emailId: true` for Gmail recognition; backfill/delta do include it explicitly.

Maildock preserves `emailId` as `providerEmailId` in normalization (`src/modules/accounts/infrastructure/imap-smtp-mail-provider.ts:464`) and `messages.providerMessageId` in persistence (`src/modules/mail/application/message-service.ts:80`). Recognition **does not implement cross-folder deduplication**: `persistBatch` checks `(mailboxId, uidValidity, uid)`, then generates a new message UUID for a new placement (`:393`, `:438`). Schema has no unique `(accountId, providerMessageId)` constraint (`src/shared/infrastructure/database/schema.ts:852`, `:894`); body cache is keyed by local message ID (`:1050`). Existing use of provider IDs to suppress command-related notifications (`message-service.ts:486`) is not shared message storage. RFC Message-ID is also not a safe substitute for provider identity.

Discovery requests sync for every selectable folder (`src/modules/mail/application/mailbox-discovery-service.ts:77`); delta poller and backfill poller independently enumerate eligible folders (`delta-sync-jobs.ts:145`, `backfill-sync-jobs.ts:130`). No Gmail All Mail/label exclusion is present. Recent/delta folders may run concurrently, with serialization for the same mailbox; historical jobs run one chunk at a time in the local backfill worker. Every label adds search/FETCH/persistence/token-acquisition work. All Mail and overlapping labels can duplicate metadata rows, transactions and later body downloads. The multiplier depends on actual memberships, not simply folder count. This increases shared load and OAuth acquisition frequency, but does not directly insert sync jobs ahead of body jobs in their queue.

Google's [Gmail client troubleshooting](https://support.google.com/mail/answer/7126229?hl=en) describes up to 15 clients per account and simultaneous-connection errors. Treat this as a provider constraint/headroom warning, not an application-enforced ceiling or proof of incident throttling. Other clients consume capacity too; byte/rate/session limits depend on account/provider policy and must be checked for the actual deployment.

Future opportunities: measure repeated provider IDs by account; share provider-identity messages/bodies while retaining folder-specific UID/flags/epoch placements; evaluate an All Mail plus label-membership model. These require identity/command/deletion/search/notification correctness design and possible migrations. No Gmail-specific optimization belongs in this investigation or the minimal scheduling hotfix.

The smallest robust architecture is the existing isolated interactive queue plus resource-aware background admission. Keep some background progress under continuous interactive traffic via bounded fairness/aging and maximum background deferral. This gate limits how many background token operations can be ahead of a body request, but cannot interrupt one already holding the OAuth row lock. ## 8. Compatibility with v1.1.0 automatic body prefetch

Reserve the current body queue for interactive work. Add separate incoming-prefetch and historical-body-backfill lanes, using background account admission and bounded concurrency. Interactive is the highest service class; new incoming bodies receive background service; historical body backfill is lowest. Numeric priorities can order eligible jobs within a lane, but cross-lane preference comes from reserved workers/resource admissions and fairness, not priority numbers alone.

The content service can remain the shared retrieval implementation, but state claiming/deduplication must become shared across all lanes and worker processes. Current singleton keys are queue-scoped and include placement; they cannot prevent interactive and prefetch jobs in different queues from downloading the same local body. An interactive request encountering an already-pending low-priority backfill must promote/reuse the durable operation or schedule safely on reserved capacity with a single authoritative claimant; simply returning false on `pending` leaves it waiting in the slow lane. Recheck ready/epoch before downloading, make completion conditional on ownership/attempt, and release claims crash-safely. Do not reset shared `fetching` state merely to promote work. Gmail cross-label identities remain a separate design.

Bound each background body job and permit checkpointed yielding; preserve regular background service so continuous interactive requests do not starve incoming caching/history forever. Prefetch must not consume the reserved interactive slot, spawn an unbounded per-message connection fan-out or hold a large account token-request backlog.

Synchronizing MIME bodies must perform **no external HTTP resource fetching**. Trusted-sender policy remains a display decision in `EmailRenderingService.render` (`src/modules/mail/application/email-rendering-service.ts:39`). Sanitization keeps inert remote references (`src/modules/mail/infrastructure/sanitize-email-html.ts:265`); background workers must not call the rendering/trust/resource-loader path to activate them. Inline CID MIME parts are local provider data, distinct from remote images; automatic attachment caching is a separate scoped policy.

## 11. Production reliability addendum: “The connection timed out.”

### Observed evidence and precise conclusion

The supplied screenshot shows the body reader's failed-state presentation: red error text **“The connection timed out.”** and the **“Retry download”** button. This exactly matches `src/components/message-reader.tsx:170`: the branch requires `detail.content.status === "failed"` and displays `detail.content.error`. The button's existence is not evidence that automatic job retries are exhausted, nor proof that a particular socket timer expired. The screenshot contains no request/job ID, attempt, timestamp, account authentication method or protocol-stage metadata.

For the reviewed build, this text is generated at `src/modules/accounts/infrastructure/imap-smtp-mail-provider.ts:287`. It is the allowlisted description of `connection_timeout`; it is **not** the original exception's message and does not specifically mean TCP connection establishment. The adapter classifies `code === "ETIMEDOUT"` or a lowercased message matching `/timed? out|timeout/`, after authentication/STARTTLS/TLS checks (`:247`, `:255`, `:269`). Consequently `Error('Socket timeout')` with code `ETIMEOUT` matches by **message**, while other messages can match the same regex. Preceding classification rules can also override a timeout-like message if it contains authentication/TLS terms.

**Confirmed:** the normal current-code path is a provider operation failure persisted by the content worker and read back by the frontend. **Not confirmed:** the original exception's code, command/stage, whether this was the first attempt or a retry, and whether Gmail/background load caused the failure. The most directly matching built-in ImapFlow exception is `Error('Socket timeout')`, code `ETIMEOUT`, but claiming it was the actual production exception would require runtime evidence. A native `ETIMEDOUT` or another timeout-worded protocol error can produce the same UI string.

### Exception and error propagation

1. **Dependency:** ImapFlow can reject `connect()`/command/download promises or emit an asynchronous `error`. Its socket timeout constructs `Error('Socket timeout')`, code `ETIMEOUT` (`node_modules/imapflow/dist/esm/imap-flow.js:1054`). During pending session initialization, `emitError` rejects the initial connection promise; afterward it emits `error` and schedules close (`:270`).
2. **Lifecycle guard:** `guardImapClient` observes the first asynchronous error, records it and closes the client (`src/modules/accounts/infrastructure/imap-client-lifecycle.ts:16`). It checks before subsequent calls, after fulfilled non-mutation promises and around iterators; `assertImapHealthy` checks before body-provider success (`:80`). This is how an asynchronous timeout can become an awaited provider failure. Rejected protocol promises/stream failures can instead surface a secondary connection/stream error; the guard's promise wrapper has no rejection handler that universally substitutes the recorded first error. Do not assume every failure preserves its original timeout code through close races.
3. **Adapter:** `fetchMessageContent` catches the error and constructs `MailProviderOperationError(sanitizeError(error, 'IMAP'))` (`src/modules/accounts/infrastructure/imap-smtp-mail-provider.ts:1471`). The public exception has `name = 'MailProviderOperationError'`, `category = 'connection_timeout'`, message **“The connection timed out.”** (`src/modules/accounts/domain/mail-provider.ts:43`). The original exception/code/stage/cause is not retained by this class. Stream failure first destroys/finishes the download stream (`imap-smtp-mail-provider.ts:1415`). Cleanup is attempted in `finally`.
4. **Content worker:** `MessageContentService.run` preserves this public message as `reason`, upserts `messageContents.status = 'failed'` and `error = reason`, then throws a new plain `Error(reason)` (`src/modules/mail/application/message-content-service.ts:249`). This loses the typed category at the next boundary. Its conflict update does not overwrite an already-ready row (`:261`).
5. **pg-boss handler:** `registerContentWorker` runs through `safeJobHandler` (`src/modules/mail/infrastructure/content-jobs.ts:70`). The wrapper catches the failure and throws `SafeJobFailure('message-content')` (`src/shared/infrastructure/logging/diagnostics.ts:78`, `:88`), with generic `internal_error`, no original cause/stack. pg-boss receives a rejected job and applies its configured retry policy. Job failure output is not the reader's source of the timeout text.
6. **API:** the enqueue POST normally already returned 202; it does not await this exception. Subsequent detail GET calls `detail`, which returns cached `content.error` only for `failed` (`src/modules/mail/application/message-content-service.ts:119`). A successfully handled GET can therefore return **HTTP 200 containing a failed body status**. The timeout is neither necessarily an HTTP 500 nor an API request abort.
7. **Frontend:** selection polling sets the returned detail, then schedules another poll only for not-fetched/pending/fetching (`src/components/mail-client.tsx:1174`). Failed content shows the error/button and stops that polling. `retryContent` POSTs again, sets local pending, increments `retryNonce` and restarts observation (`:1223`). A scheduled false response is still accepted, so clicking Retry does not guarantee a new immediate execution. A durable existing retry/successor can still govern when work starts.

ImapFlow's socket timer is **inactivity-based**, not a total FETCH deadline. Quiet sessions with open downloads/held locks/IDLE and no stuck command can trigger a recovery NOOP instead of immediate failure (`imap-flow.js:1056`). A stuck command triggers the error branch; a stalled recovery NOOP can fail on a later timeout. `download` itself may issue multiple partial FETCH commands (default 64 KiB chunks, MIME metadata and sometimes BODYSTRUCTURE; `imap-flow.js:2917`, `:2931`, `:2977`). “Message fetching” therefore comprises command setup and stream/chunk progress, not one indivisible network call. Worker event-loop stalls may delay command processing/timers; they do not prove Gmail stalled.

A 15-second inactivity timeout plus queue wait, credentials, setup, cleanup and browser polling is **compatible** with an approximately 20-second user-visible failure. This is a timing hypothesis, not an observed decomposition. Increasing priority cannot repair an active connection that stopped making progress.

### Recommended reliability fix and production diagnostic gate

Treat the new evidence as a retrieval failure requiring recovery correctness, stage diagnostics and controlled fault validation before performance tuning. The user-visible error must stay safely sanitized; enabling raw ImapFlow logging would expose protocol/message/authentication data and is not an acceptable diagnostic shortcut.

1. **Preserve safe failure identity before it is lost.** Add allowlisted `operation = message-content`, stage (connect/session, mailbox-open, part-download, stream, cleanup), normalized timeout kind/code, attempt/job/correlation ID and monotonic elapsed time at the provider boundary. Record socket inactivity separately from total attempt time and last part progress; log byte counts, never part contents or server responses. Capture the guard's first asynchronous safe failure classification alongside any secondary close/stream error without altering acknowledged mutation semantics.
2. **Correct timeout classification explicitly.** Add code-based handling for the pinned dependency's `CONNECT_TIMEOUT`, `GREETING_TIMEOUT`, `UPGRADE_TIMEOUT`, `ETIMEOUT` and `ETIMEDOUT`. Keep stage/kind distinct internally while retaining safe public text. This is a confirmed classifier defect worth fixing independently of the incident's unknown failing stage. A suffix/substring fallback must not cause TLS/authentication errors or untrusted server text to become misleading diagnostics. Do not simply expose original exceptions to the UI or pg-boss output.
3. **Make retry state truthful and recoverable.** Audit the current persisted failed state versus automatic retry and manual successor. Represent a transient failure with an authoritative retry operation/status that the frontend can continue observing, or explicitly make failure terminal and manual retry the chosen policy. Preserve bounded attempts/backoff and deduplication; do not repeatedly POST or reset pending state based on frontend elapsed time. Keep permanent credential/UIDVALIDITY/size failures distinct from retryable transport stalls. Agree this behavior before implementation; currently a successful automatic retry can go unobserved after the failed UI stops polling.
4. **Fix the measured resource cause.** If high concurrent sessions/token demand correlates with stalled IMAP commands, apply bounded background admission before credentials with interactive headroom as recommended in section 6. If a healthy Gmail connection regularly makes legitimate progress only after the hardcoded 15-second idle threshold, evaluate a configurable, bounded socket-timeout increase using controlled/real-provider measurements. A blanket timeout increase can hide broken connections, occupy the sole body slot longer and worsen reliability for other selections; it is not the first recommended fix. A total attempt deadline/cancellation policy would need separate cleanup and recovery design.
5. **Fault-test the entire propagation and recovery path.** Extend the proposed later test plan with actual stalled TCP/TLS, no greeting, stalled session/authentication, stalled folder-open, first FETCH/next chunk stall, unexpected disconnect and cleanup-only stall.
