### Supported adapter proposal and upgrade risk

Create a narrow owned-client interface with complete interval SEARCH, exact metadata FETCH, exact-known-set membership/flags, refresh/select, raw MIME slice and mutation/APPEND calls. Each receives one turn context with deadline, budget, epoch and cancellation guard; each returns tagged command evidence plus structured completeness/uncertainty diagnostics. Business callbacks cannot call ImapFlow directly. Healthy command completion preserves reusable authentication; failures invalidate token first, destroy socket and await settlement.

Promote the **contracts** exercised by `experiments/imap-transport/hardening.ts`, `experiments/imap-dovecot/client.ts` and `experiments/imap-durability/client.ts`, not imports of their implementations. Public parser caps/close are reusable. Private `getUntaggedHandler`, raw `exec`, socket listener ordering, logger parser diagnostics and partial-origin token interception need supported additive hooks or a small isolated pinned patch. Propose command-scoped parsed-result/error/completion hooks, raw `{section, origin, length, encoding}` exposure and an aggregate post-decompression input guard. Reject missing SEARCH evidence even after tagged OK, and unsolicited flag-only rows must not satisfy metadata. No strict parser K patch is required under the approved byte contract.

The existing STORE patch covers ESM and CJS; any adapter addition must preserve both runtime paths and its conditional errors. Every dependency update requires source diff plus retained omitted/depth/wrong-origin/trickle/DONE/unsolicited/ESEARCH/STORE regressions. Conservative logger fallback can falsely reject a compatible server; it is not a stable correctness API. Compression/rev2/BINARY/ESEARCH remain unsupported until the bounded fallback/negotiation is tested. No whole-library fork is proposed.

### Production DB boundary proposal

Recommend explicit reserved-client BEGIN/COMMIT/ROLLBACK plus scoped Drizzle-compatible business queries on reusable receiving-only single-connection lanes. Forced retirement permanently ends one lane; it cannot cancel shared web/SMTP/OAuth/pg-boss clients. Total D and deployment connection limits include all pools; this is no extra worker fleet. Compare retaining a shared callback transaction until genuine settlement (safe only if settlement is proved, but unbounded callback can obstruct reuse) and experimental socket/PID interception (precise in plaintext fixture, private/TLS/startup risks). Lane retirement is the simpler public-client lifetime boundary, **RECOMMENDED and unvalidated in production**. The original late-rollback failure and prepared DELETE must pass before adopting it.

Use READ COMMITTED with explicit lease/account/mailbox row locks and revision CAS; do not substitute SERIALIZABLE for ownership or expiry. Take shared lease then lifecycle then sorted mailbox locks, followed by existing threading/event locks in a consistent documented order. Any account-disable/discovery writer participates in lifecycle/epoch/revision exclusion. Short authoritative transactions contain metadata, justified frontier, relevant command/content outcome and unique notification event; no IMAP I/O and no broad retention cleanup. If COMMIT is unknown, retire and establish old-backend ordering before fresh state reload/retry. [Architecture §14](SYNC_ENGINE_ARCHITECTURE.md#141-commit-authority-and-its-linearization-point) compares authority alternatives and recommends a deferred commit check at logical L; exact WAL-durability-before-expiry remains OPEN.

## Multi-folder and provider acceptance

INBOX initialization precedes secondary bootstrap but does not require a complete LIST first: select standard INBOX, establish its bounded metadata, then discover/rotate selectable folders. Missing/unsupported INBOX or uncertain identity is explicit failure, not a fabricated row. Each folder has separate F/E/R/epoch/revision/due. Secondary fresh checks have bounded revisit through maintenance/rotation, not a history-complete gate. Explicit user access promotes a folder's next operation while account current alternation remains. Moves schedule source/destination fresh and repair; they do not transfer a UID or imply an atomic remote snapshot.

Stable `MailboxService.reconcile` matches optional provider IDs or active paths and marks absent local folders missing after a whole list. Stable tests cover path reuse/new UUIDs, missing/manual/special-use mappings and epoch changes, but do not prove full new-engine multi-folder scheduling. Without stable mailbox IDs, do not infer rename from matching counts/name; conservatively treat old path missing and new path independent, preserve user role mapping until explicit evidence/manual repair. Review complete LIST publication and bounded DB finalization before discovery implementation: if limits cannot accommodate a provider's folder set, keep old topology and surface incompatibility rather than delete based on partial listing.

## Recommendation and approval boundaries

Proceed to staged planning using the existing application structure and vertical milestones. Do not begin production implementation from this documentation task. User decisions remain OPEN for the recommended logical commit boundary/trigger, mailbox revision, receiving DB lane lifetime, adapter patch surface, numerical latency/size/fairness/overload settings, degraded APPEND behavior and notification classification of offline arrivals. A stronger physical commit-expiry requirement would need a different proven mechanism. Engineers can review isolated stage proposals against these gates without accepting the whole release. All-fresh/history/repair correctness, queue delivery, business compatibility, multi-folder/provider/MIME tests and new history policy must pass before release.
