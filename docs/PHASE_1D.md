# Phase 1D: on-demand message content

Metadata synchronization stores only envelope, flags, placement, and normalized BODYSTRUCTURE. Opening a message reads PostgreSQL immediately. If `message_contents` has no ready body, the browser requests a pg-boss `message-content-fetch-v1` job and polls the local detail endpoint every 2.5 seconds until ready or failed. Jobs contain only version and local account, mailbox, and message UUIDs. Ready content is read without IMAP, including after browser refresh or an IMAP outage.

The worker validates account, mailbox, placement, and message ownership; account enabled state; mailbox active/selectable state; and the stored placement UIDVALIDITY against the last synchronized mailbox UIDVALIDITY. The provider opens the mailbox read-only and compares its currently selected UIDVALIDITY before downloading. UID is always scoped to that mailbox and UIDVALIDITY.

`selectDisplayParts` walks normalized BODYSTRUCTURE. A single-part text root with no ImapFlow part identifier maps to part `1`, which ImapFlow downloads through its special single-part `TEXT` handling. It skips attachment disposition and filename-bearing branches. An alternative chooses the last plain and last HTML candidate. A mixed/related structure uses its first usable body branch. It never selects images, application parts, or text attachments. No attachment binaries, CID resources, or raw RFC822 source are downloaded or stored.

The provider uses ImapFlow `download(uid, part, { uid: true, maxBytes: limit + 1 })` sequentially for selected text parts. ImapFlow emits `BODY.PEEK`/`BINARY.PEEK` for these requests, so reading content does not set `\Seen`. Its download pipeline decodes base64 and quoted-printable, handles server-side BINARY responses without double decoding, and converts known charsets (including legacy Western charsets) to UTF-8. Unsupported charset metadata fails safely. The default `MAILDOCK_MAX_MESSAGE_TEXT_PART_BYTES` is 5 MiB per selected part, configurable up to 20 MiB. A part over the limit fails; sanitized HTML is also capped before storage.

Server-side DOMPurify 3.4.16 with jsdom 30.1.1 and HTML-only profile produces `email-html-v1`. Scripts, forms, embeds, frames, SVG, MathML, style elements and attributes, media, images, and active/resource tags are removed. The final DOM pass retains only inert display attributes and explicit http/https/mailto links. IDs, names, remote URLs, and sender-controlled targets are removed. CID images remain unavailable. A remote-content indicator reports removed resource-bearing markup. Raw HTML is not persisted.

Maildock wraps sanitized body fragments in its own iframe document. The iframe has an empty sandbox attribute, an opaque origin, no scripts/forms/popups/top navigation, `no-referrer`, and a document CSP with `default-src 'none'` plus explicit `script-src`, `connect-src`, `img-src`, `font-src`, `media-src`, `frame-src`, `object-src`, `form-action`, and `base-uri` set to `'none'`. Frame-local `style-src 'unsafe-inline'` permits only Maildock's static readability CSS; sender styles are removed before persistence. No global CSP relaxation is required.

Failures store generic or fixed sanitized messages. A ready body is never replaced by a failed retry. Attachment metadata is informational only. Account management and prior diagnostics remain available under `/accounts`.
