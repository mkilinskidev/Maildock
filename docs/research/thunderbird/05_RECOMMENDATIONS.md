# Independent recommendations and remaining evidence

Research only; no synchronization design is approved for implementation. Thunderbird **5ac95865d39e426e66122ef4f54907ffa474a579** and stable Maildock **ba074880768645473af070ecc846e420ced990d5**, inspected **2026-10-11**. Evidence Txx resolves through [source map](01_SOURCE_MAP.md), Mxx through [comparison](04_MAILDOCK_COMPARISON.md).

## Recommendation

Start a fresh architecture discussion around **short provider operations, durable idempotent persistence, explicit resource ownership and repair**. Do not start with the old v2 contracts or translate Thunderbird's C++ structure into TypeScript.

Thunderbird provides good evidence for separating metadata from content, identity-based reconciliation and rebuilding body work from durable availability. It does **not** provide a verified solution for new INBOX mail bypassing a long initial same-folder header update. Its body priority mechanisms must not be used as proof of header responsiveness (T05, T09–T10, T16–T18).

The research is strong enough to begin a **new architecture design with explicit open questions**. It is not strong enough to approve final cursor rules, a freshness guarantee or implementation. Critical correctness/timing experiments below must precede those approvals.

## Smallest plausible architecture

This is a candidate set of responsibilities, not a finalized component/API/schema plan:

1. **Wakeup and due-work selection.** Account setup, polling, IMAP notifications, Gmail notifications and user requests signal work. Select an operation kind by urgency and available account resources. Browser presence is irrelevant.
2. **One bounded execution framework.** Run an adapter operation for arrival discovery, historical ingestion, reconciliation or a user command. Finish a meaningful evidence unit, commit results, release ownership/transport, then reconsider priority before continuation. Separate urgency does not require two synchronization engines.
3. **Provider-specific state and evidence.** IMAP preserves folder epoch/UID identity and distinguishes arrival progress from historical coverage; conditional flags cannot stand in for complete membership. Gmail preserves its own account history and listing semantics. Do not finalize how many cursor fields are required until replay and overlap cases are proven.
4. **Shared persistence/publication.** Idempotently store placements and metadata in PostgreSQL, with whatever durable progress those stored results justify in the same transaction. Publish committed metadata promptly. On-demand content/attachments retain independent availability and limits.
5. **Repair and retry.** Periodic checks restore unfinished work and reconcile stale state. Failed ownership attempts defer without consuming all urgent retry budget; interrupted transactions are replayed. Sending/drafts/OAuth/attachment workflows remain supported.

A single execution framework can have several operation kinds and priority classes without durable bootstrap phases or separate foreground/background call stacks. **Inference/proposal:** this can be smaller than v2's staged bootstrap while meeting product requirements, provided that cursor advancement never claims unpersisted coverage and a pending wakeup cannot vanish. T17–T20 and M05–M09 support those conditions, not a fully specified implementation.

No mechanism is removable solely because Thunderbird lacks an equivalent. The reduction must preserve the chosen product guarantee or explicitly trade it for a tolerated delay/replay cost. In particular, no concrete final Gmail checkpoint or pagination algorithm follows from this table.

Historical values such as 30 days / 200 / 50 are not selected. Thunderbird's 10-header transfer and roughly 2 MB body group also do not prescribe Maildock metadata limits. New-install targeting removes an in-place v1 migration obligation, not the need to preserve sending, drafts, OAuth and attachments.

## Five most valuable findings

1. **Headers are a separate active path from AutoSync.** SELECT/NOOP → UID/flags → missing-header fetch → DB publication runs through folder/service/protocol/parser/sinks. AutoSync chiefly adds offline content scheduling and can initiate normal folder updates (T01–T18).
2. **Progressive publication is not preemption.** Ten-header DB transfers coexist with a potentially huge active FETCH/dump loop; same-folder connection affinity waits behind active work. The requested fresh-mail bypass is not established (T04–T05, T09–T13).
3. **Optimizations have a real fallback.** CONDSTORE is preference-gated and defaults false; partial flag state cannot prove deletions. No QRESYNC/VANISHED path was found. Full UID/flag reconciliation remains material (T07–T08, T14).
4. **Durable local facts support repair without a durable copy of every queue.** Existing headers/epoch/properties and offline availability survive normal persistence; AutoSync queues/retries are transient. This is not a transactional bootstrap checkpoint guarantee (T08, T11, T17, T19–T20).
5. **Maildock v1's concrete blockers differ from its reusable safeguards.** Alphabetic equal-priority bootstrap and recent-success gating delay INBOX/fresh discovery; long delta repair spans hold the same execution lock. Batch transactions, gap handling, epoch checks and confirmed absence are worth retaining (M01–M09). Stable v1 uses Google IMAP/SMTP; native REST must be designed separately (M12).

## Three significant simplification opportunities

1. **Unify orchestration:** operation kinds in one execution/ownership model could replace separate recent/delta/history lifecycle machinery and remove initialization as a prerequisite for scheduling fresh checks. Coverage still needs provider-specific proof.
2. **Move expensive repair out of the urgent arrival operation:** bounded, periodic flag/membership reconciliation could replace all-known-UID scanning on every delta, with an explicit acceptable stale-state interval.
3. **Reduce persisted intermediate structures:** reuse unique placements, content availability and transactional provider progress to recover work rather than adding staging stores, receipts and scheduler frontiers by default. Preserve any structure that is the only reliable coverage evidence.

## Critical unresolved questions and proposed experiments

These experiments are future research; none was executed here, and none is an implementation authorization.

| Question                                                                 | Evidence missing / discriminating experiment                                                                                                                                                                          | Design consequence                                                                                                      |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| What actually happens to ten arrivals during initial 50k-header FETCH?   | Controlled fake IMAP server, timestamps at flags capture, header UID capture, last FETCH and IDLE entry; inject EXISTS in each window. Observe next SELECT/NOOP and message-added time. No inspected test covers it.  | Establish whether wakeups are lost/coalesced and what bounded trigger is necessary; do not promise Thunderbird latency. |
| Which limits bound fresh-mail latency?                                   | Measure network command time, DB publication/commit time and lock duration for dense/sparse UIDs, large headers and slow server responses with 1/2/5 connection budgets. Include commands and text/attachment access. | Choose budgets from worst-case service units rather than count alone.                                                   |
| How large is v1's repeated membership cost?                              | Read-only benchmark design for 50k known placements: count SEARCH/FETCH calls, elapsed scan, DB-pool reservation and retry contention. Compare arrival-only work plus periodic repair.                                | Decide repair cadence and whether full membership scans need a separate cursor.                                         |
| Can progress be simplified without receipt sets?                         | Fault-injection model for searched-but-unfetched UID, out-of-order results, concurrent expunge/arrival, UID gaps, commit success followed by enqueue failure, duplicate workers, epoch reset.                         | Demonstrate no skipped identity or justify retained coverage structures.                                                |
| What is safe Gmail historical/history overlap?                           | Further official REST analysis plus controlled list/history races, expired history cursor, label changes and repeated page delivery. Stable Maildock has no REST implementation to inspect.                           | Design opaque provider state; no final cursor/page-token commitment yet.                                                |
| What survives an abrupt local store/DB crash in Thunderbird?             | No instruction-level crash matrix or Gecko/Mork durability proof was inspected. | How reliable is conditional expunge detection with simultaneous churn?   | Source uses count sanity and full fallback, but dedicated CONDSTORE coverage was not located. Test equal net-count arrival/deletion cases and server quirks.                                                          | Keep explicit deletion evidence/repair rather than relying only on counts.                                              |
| How should failed remote connection admission change the account budget? | Configured Thunderbird cap found; exhaustive adaptive rejection policy not traced. Secondary gaps: complete offline command replay and cross-folder move recovery, full attachment route selection, production-default variations, and latest-source versus deployed stable Thunderbird behavior. Upstream main was deliberately pinned as requested; findings are not a retrospective guarantee for every released version.
