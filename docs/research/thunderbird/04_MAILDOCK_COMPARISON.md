## Why another folder can precede INBOX

The evidence chain is `AccountsService` → discovery → `MailboxService.listForAccount` (alphabetic `remotePath`) → concurrent scheduling → recent jobs with equal priority (M01–M03). There is no explicit INBOX boost in this path. **Inference:** a path sorting before INBOX can enqueue and begin first, subject to queue timing/concurrency. Alphabetic order plus concurrent scheduling is not a promise that the exact execution order always matches path order.

Thunderbird's `GetNewMessages` directly requests INBOX before non-INBOX checks (T02), and its _body_ priority strategy also favors INBOX (T16). Maildock can adopt explicit initial INBOX preference without copying desktop body scheduling or requiring identical folder order across all operations.

## Why fresh mail can wait

1. **Before recent initialization:** watcher/poller/delta eligibility requires recent success (M04). Recent synchronization captures SEARCH results once and fetches all of them under the same execution lock (M03, M08). **Inference:** an arrival after SEARCH can wait for job completion and a later eligible discovery trigger. Batch DB commits give visibility but do not release the lock or restart the provider's UID discovery.
2. **After initialization:** delta retrieves new UIDs before flags/removals (M05), which is useful. But the same job continues scanning known local messages, and the worker holds the execution lock for the whole call (M08). A second delta or mailbox command may fail to acquire the lock and enter queue retry even after arrivals have been detected by a separate watcher.
3. **During history:** history already uses one bounded window and yields via continuation (M06–M07). Pending recent/delta checks are useful, but work enqueued after the final check cannot preempt the active window. Numeric priorities on different queues do not themselves establish one shared priority order. This is a conclusion about the inspected independent `boss.work` registrations, not an audit of every pg-boss internal behavior.

Thunderbird similarly separates progressive header publication from transport scheduling and serializes busy same-folder operations (T05, T09–T10). It therefore supplies patterns and cautionary evidence, not a verified solution to Maildock's highest-priority freshness problem.

## Existing mechanisms worth retaining

- **Atomic batch/progress:** `persistBatch` transaction couples stored metadata with delta frontier and history frontier; test bodies verify rollback and idempotent retries (M09).
- **Known absence only:** successful SEARCH over known placements precedes removals, without importing unrelated history (M05).
- **Gap safety:** an omitted FETCH prevents advancing delta beyond the first omitted searched UID; history rechecks whether omitted UIDs still exist (M05–M06).
- **Epoch isolation and stale-flag protection:** UIDVALIDITY checks, placement identity and MODSEQ comparisons protect reused UIDs and older results (M03, M09–M10).
- **Server operation without browser:** dedicated worker/watchers/pollers and durable jobs already exist (M11). This need is not a reason to discard all v1 machinery.
- **Lazy content/OAuth/outgoing features:** synchronization redesign must preserve their product behavior and existing boundaries. This research did not re-audit sending, drafts or all OAuth paths; no deletion recommendation covers them.

## Responsibility and contention findings

`ImapSmtpMailProvider` combines verification, folder discovery, three synchronization modes, commands, content, attachments and outgoing-related protocol work. `MessageService.persistBatch` combines metadata/placements with conversation assignment, local-command/outgoing reconciliation and notifications (M03, M05–M06, M09–M10). **Assessment:** these are concentration points for future simplification, not proof that every concern should become another independently scheduled service.

The execution lock consumes a reserved PostgreSQL connection while network work runs. Contention throws immediately; a later urgent job does not take ownership from history. Distinguish this execution lock from the short transactional producer coalescing lock: they solve different races (M07–M08). Removing either without alternative ownership/deduplication evidence could regress correctness.

Each operation constructs a new IMAP client while an INBOX watcher maintains another. No account-wide cap was found in the inspected composition/provider/watcher code (M04, M10–M11). **Inference:** aggregate concurrency and connection churn can exceed restrictive server budgets, including when body/command jobs run concurrently. Server-limit failures and DB-pool starvation require measurement; their frequency cannot be inferred from code alone.

## Opportunities to remove whole mechanisms

**Candidate 1:** replace separate recent/delta/history orchestration and success gates with operation kinds under one scheduling/ownership model. Provider state still needs separate semantics for arrival discovery and historical completion; deleting the gate does not justify advancing a cursor over unseen work.

**Candidate 2:** decouple arrival discovery from all-known-UID flag/deletion repair. Repair could become periodic bounded work rather than part of every fresh-mail delta. This reduces urgent lock duration and repeated complete scans, at the cost of delayed external flag/deletion visibility. The acceptable delay must be decided before removal.

**Candidate 3:** use persisted placements/content availability and a few provider progress values to repair work, reducing derived queues/frontiers/staging/receipts. v1's batch transactions and unfinished-history poller already demonstrate parts of this approach. Missing-fetch coverage and Gmail pagination still require proofs; simplification cannot remove the only evidence that a range was processed.

These candidates challenge old v2 concepts without editing v2 contracts. They are architectural alternatives for fresh installations, not an approved implementation or migration plan.
