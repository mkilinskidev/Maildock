# F8 authentication/MFA throttling implementation and validation

Reviewed 2026-10-06 against base commit `f4604724d884d4cd0926ec29411df1830ae1fb25`, using `docs/SECURITY_F8_DISCOVERY.md` as the authoritative discovery baseline. Changes are local and uncommitted. No push or deployment was performed. F2 and F3 remain closed; F9 is separate and unchanged.

## Architecture and findings

F8-G1 is resolved by two persisted, shared single-owner management reauthentication budgets. F8-G2 is resolved by checking and updating canonical password backoff **inside the existing credential transaction**, after taking PostgreSQL advisory transaction lock `1296125023` (M), at READ COMMITTED. F8-G3 is resolved by independently committed, atomic work reservations **before acquiring M**. F8-G4 is resolved by using the existing 4096-byte/10-second streamed JSON boundary for username sign-in and explicitly enforcing the shared 12..128 password policy.

`auth-admission.ts` is a small application-specific module, not a generic limiter. Migration `0031_auth_admission.sql` creates `auth_admission(key, count, expires_at)`. A database CHECK restricts the table to exactly five keys. Work reservations use one `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING`; their count/expiry decisions use the same incoming database-clock instant (`EXCLUDED.expires_at`). The independently committed root-database reservation survives later verification failure, transaction rollback, or process failure. Denied reservations saturate at limit+1, never extend expiry, and perform no credential verification or M wait. Expired windows restart atomically at count=1. PostgreSQL is the sole correctness dependency.

The management keys are owner-scoped through immutable single-owner binding: only a valid READY owner session can reach their checks or writes. They deliberately do not incorporate a session, submitted username, factor ID, challenge, route, or IP. Replacing the authenticator therefore does not manufacture a new management failure bucket. Unauthenticated callers can spend the separate management **work** bucket but cannot spend these proof buckets.

Login's HTTP protocol schema is derived directly from installed Better Auth 1.7.5 `signInUsername.options.body`, extended only with the shared password schema and made strict. The installed plugin retains its username grammar, 3..64 length, case normalization, `rememberMe`, and `callbackURL` semantics. Login still does not trim the actual identity. `ownerPasswordSchema` is also reused by setup, initial MFA and management; their existing 12..128 policy is unchanged. Better Auth's configured password min/max reference the same constants. No unbounded clone/JSON parse remains in the catch-all.

The streamed boundary checks exact Origin, JSON Content-Type, declared length, actual streamed bytes, strict JSON shape and password size before work admission. UTF-8 decoding is fatal. Its absolute read deadline is 10 seconds, not renewed per chunk. A validated JSON body is reconstructed for Better Auth. Malformed JSON/shape/password returns 400; oversized/stalled body returns 413; non-JSON returns 415. None reaches Argon2. Expected authentication failures remain generic; proof values and counts are not added to responses or logs. New 429 responses use `Retry-After` and `Cache-Control: no-store`. Username HTTP responses additionally copy Better Auth's `X-Retry-After` into `Retry-After`; anonymous MFA account-lock responses now expose the remaining persisted lock duration through the standard header.

The small work budgets separate password hashing from MFA so a spent password window does not automatically prevent the owner from finishing an existing challenge. Twelve password requests/minute permits interactive retries and several complete logins while bounding even unknown-user dummy Argon2. The existing per-client L1 is stricter for a single client. Thirty MFA operations/minute permits a ceremony, correction, cancel, and resumption but bounds invalid-authority requests before they queue M. Twelve management operations/minute is ample for infrequent administrative changes and caps even repeated correct proofs; a successful management operation retains the reviewed second framework password check. Five management errors in fifteen minutes is a deliberately small online guessing budget for password-plus-current-factor reauthentication without coupling it to anonymous account locks.

## Transaction and availability semantics

Expected wrong management passwords and the installed plugin's `INVALID_CODE`/`INVALID_BACKUP_CODE` failures return generic error responses **inside M**, so their stage counters commit. The sensitive operation exits immediately on these responses. Other API/infrastructure errors still throw; actual MFA/session/authority changes retain the existing rollback guarantees. A correct recovery proof still uses the resolved patched adapter's conditional UPDATE/CAS. Consumption, generation/replacement and successful counter resets commit together; a subsequent operation/commit failure rolls them all back. Independently reserved work is never refunded. Returning a response does not make actual state-transition failures commit.

Password-stage success clears L2 before MFA, as before. It does not clear L7 or either management factor counter. Correct management password clears only management password; correct management factor clears management factor. Regeneration replaces the recovery set without resetting anonymous failures; replacement still requires old password + old current factor, revokes sessions/challenges, and verifies the new factor under L8. The existing replacement of the factor row is unchanged; its new anonymous factor state is available only after the fully authorized replacement ceremony.

| New/changed bucket  | Who can spend it / anonymous access                                                                              | Automatic recovery and maximum single denial                                                                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| W-password          | Any caller with Origin and syntactically accepted login JSON, independent of username existence                  | Next admission after fixed 60s expiry; success does not reset; denied calls cannot prolong that expiry.                                                                  |
| W-MFA               | Any caller with Origin and the route's strict valid body, even without challenge/replacement authority           | Same fixed 60s recovery; success does not reset.                                                                                                                         |
| W-management        | Any caller with Origin and strict valid management JSON, even without READY session                              | Same fixed 60s recovery; success does not reset.                                                                                                                         |
| Management password | Only valid READY owner-session holder submitting an incorrect owner password                                     | Successful password before exhaustion or fixed 900s expiry; maximum remaining denial 900s from first failure, not a new 900s after each denial.                          |
| Management factor   | Only READY owner-session holder who also knows the password and submits an incorrect current TOTP/recovery proof | Successful factor before exhaustion or fixed 900s expiry; password success cannot clear it; maximum remaining denial 900s.                                               |
| L2 cleanup          | Anonymous valid submitted usernames can create existing failure state, now globally admission bounded            | Existing maximum 900s password backoff; inactive count decays by pruning after 15min with no active block. Correct password clears L2. Denied requests do not update it. |

These are per-window/per-lock bounds, not a promise of service availability during continuous hostile traffic: an attacker can spend a later work window again. No ordinary throttle requires manual operator unlock. Anonymous traffic cannot install a permanent new owner lock or extend a denied fixed window. Existing expired/exhausted replacement **ceremony** retention is not changed into a throttle reset or bootstrap escape; that pre-existing authority policy is outside this fix.

There are at most five new rows, enforced by CHECK+PK. New work admission allows at most twelve potential new username rows per fixed minute. Every admitted HTTP password operation prunes backoff state idle for at least 15min whose delay has ended. This supplies bounded inactivity expiry/cleanup for attacker-selected state, with globally bounded admission of new names regardless of IP. It is not a database CHECK imposing a hard row-count cap: admitted jobs waiting for M can write later than their reservation. Stale rows cannot keep accumulating under ordinary continued password processing, and an idle service creates no further rows. Pre-existing stale rows are also pruned on the next admitted login. No cleanup scheduler or permanent username-existence shortcut is introduced. Unknown valid names still execute Better Auth's real dummy Argon2.
